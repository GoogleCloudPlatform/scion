  ROTATING THE PASSWORD REQUIRES ONE MANUAL STEP. THIS IS THE STEP.

  When you change database.password, `helm upgrade` writes the new value into
  the settings Secret and reports success - and every running pod keeps using
  the OLD password until you also run:

    kubectl rollout restart deploy/{{ include "scion-hub.fullname" . }} -n {{ .Release.Namespace }}

  Nothing detects the omission. The upgrade is green, the Secret is correct, and
  the hub is still authenticating with the credential you just retired. If you
  rotated because the old one leaked, it is still live.

  WHY, IN ONE PARAGRAPH, SO THE STEP IS NOT MISTAKEN FOR A BUG TO BE FIXED.
  settings.yaml is a subPath mount and the kubelet never refreshes one, so the
  chart rolls the pods by digesting the settings document into a pod annotation.
  That annotation is readable by anyone who can get deployments - a wider
  audience than the Secret - and the only unknown in a DSN is the password, so
  a digest of the raw document lets that reader confirm a guessed password
  offline. The digest is therefore taken over a projection with the credential
  removed, and a change that touches nothing but the credential no longer moves
  it. Everything else still rolls the pods on its own: host, port, database
  name, pool sizes, config.extra.

  If you would rather not hold the step in your head, rotate the database name
  or the user in the same upgrade and the roll happens automatically - but do
  that because it suits your operations, not as a workaround.
{{- end }}

  THE CONNECTION BUDGET, AND THE PART OF IT WE HAVE NOT MEASURED.

  Cloud SQL enforces a hard max_connections per instance. Exceeding it does not
  degrade: new connections are refused, and the hub's refusal surfaces during
  AutoMigrate or mid-request rather than at startup, so it looks like an
  intermittent application fault. Size it before you scale, not after.

    TOTAL = R * (M + S)

    R = replicaCount                     = {{ .Values.replicaCount }}
    M = database.maxOpenConns            = {{ .Values.database.maxOpenConns }}   (the ent pool, per replica)
    S = every other connection a replica holds
        YOU MUST SUPPLY THIS. It is not a chart value and the chart does not
        guess it, because we have not measured it.

  WE HAVE NOT MEASURED S. No hub has been run against a Cloud SQL instance in
  the course of building this chart - the deploying principal is refused by
  sqladmin.googleapis.com with HTTP 403 - so there is no observation of steady
  state to report, and a number invented here would be indistinguishable from
  one. Measure it on your own instance, at your own load, with one replica:

{{- if .Values.config.existingSecret }}

    SELECT count(*) FROM pg_stat_activity
     WHERE datname = '<the database in your own DSN>'
       AND usename = '<the role in your own DSN>';

  The chart cannot fill those in under config.existingSecret: database.name and
  database.user are refused there precisely because they would go nowhere, and
  the DSN the hub dials is the one in your settings.yaml. M below is the chart's
  default rather than your value, for the same reason.
{{- else }}

    SELECT count(*) FROM pg_stat_activity
     WHERE datname = '{{ .Values.database.name }}' AND usename = '{{ include "scion-hub.databaseUser" . }}';
{{- end }}

  Take that at steady state under representative traffic, subtract M, and the
  remainder is your S. Re-measure after any change to replica count or
  workload; S is not a constant of the software, it is a property of your load.

  THE STRUCTURAL MAXIMUM, WHICH IS A CEILING AND NOT AN OVERHEAD. Read out of
  the hub's source, so it says what the code CAN open, not what a running hub
  DOES open. Do not budget with it as though it were an observation, and do not
  substitute it for S:

    S_max = 2 * max(4, NumCPU) + 2

  per replica, when database.driver is postgres. Its terms:

    - The Postgres event publisher's pool (pkg/hub/events_postgres.go:169) and
      the Postgres command bus's pool (pkg/hub/command_bus.go:113). Both call
      pgxpool.ParseConfig on this same DSN and neither overrides MaxConns -
      applyEventPoolKeepalives sets only idle time and lifetime - and the DSN
      the chart renders carries no pool_max_conns. So each defaults to
      max(4, runtime.NumCPU()) (pgx v5.9.2, pgxpool/pool.go:383).
    - One dedicated LISTEN connection each, outside those pools, held open for
      the process lifetime (events_postgres.go:486, command_bus.go:259). These
      two are not a maximum; they are always open.

  NumCPU IS THE NODE'S CPU COUNT, NOT YOUR CPU LIMIT. The hub does not set
  GOMAXPROCS and does not vendor automaxprocs, so a pod with a 500m limit on a
  64-core node still reads 64. S_max there is 130 per replica, from a container
  you sized at half a core. If you are on large nodes, this term dominates
  everything else in the budget.

  WHY IT IS A CEILING AND NOT A COUNT: pgxpool opens connections on demand and
  closes them when idle, so a quiet hub sits far below this. How far below is
  precisely the thing we did not measure.

  database.maxOpenConns must be at least 2. The hub treats a value of 1 or less
  as unset (pkg/config/hub_config.go:573) because a single-connection pool
  self-deadlocks the moment one query waits on another, so a 1 you set to save
  connections would silently become the hub's own default instead of failing.
  The schema rejects it up front rather than letting that substitution happen.
{{- end }}

  WARNING: cloudsql.nativeSidecar IS FALSE. THE HUB WILL CRASH-LOOP AT STARTUP.

  The proxy is rendered as a plain container in containers[], and Kubernetes
  gives containers in that list NO START ORDER. The hub therefore races the
  proxy for the loopback port, loses it most of the time, and exits; the
  kubelet restarts it; eventually the proxy is up and a restart succeeds. The
  pod reaches Ready after a handful of CrashLoopBackOff cycles and the events
  say "connection refused", naming nothing that is actually wrong.

  The second half is worse and is not self-correcting. Kubernetes has no
  shutdown order either, so on pod termination the proxy can exit while the hub
  is still draining, and in-flight queries fail against a socket that closed
  under them. There is no backoff that recovers from that.

  This exists ONLY for GKE below 1.29, where restartPolicy on an init container
  is not honoured. On 1.29 or later set cloudsql.nativeSidecar: true and both
  problems disappear - the proxy starts before the hub and is torn down after
  it, by the API, not by luck. Check with: kubectl version
{{- end }}

THE SETTINGS FILE IS READ-ONLY. THIS IS DELIBERATE.

  If you are here because the hub logged a warning about being unable to write
  its settings file, or because a settings change you made through the API did
  not stick: that is this mount, working. Making it writable is the wrong fix,
  and it is the fix everybody reaches for first, so here is the reasoning before
  you spend the evening on it.

  The hub rewrites settings.yaml at runtime. In a Deployment those writes are
  pod-local - the other replicas never see them, and they are lost at pod
  replacement. That alone would only be lossy. What makes it dangerous is
  syncHubSettings, which runs on every boot and re-seeds shared database state
  from the pod-local file for every section whose row is absent or still marked
  as seeded. So a pod that can write this file can promote its own local
  divergence into the shared truth every other replica then reads, at a moment
  nobody chose, with no error anywhere.

  Making the file writable does not fix that. It re-enables it. The proper fix is
  in the hub - the settings file becomes read-only in hosted mode with the
  database as the sole writable store - and it is tracked as ptone/scion#1091.
  When that lands this mount stops being load-bearing. Until then it is the only
  thing preventing the divergence, and the cost of it is a log line.

  Note the directory is NOT read-only. Only the one file is. {{ include "scion-hub.scionDir" . }}
  is the hub's whole state directory - storage/, templates/ and scion-token are
  all created in it - so mounting configuration over the directory breaks the hub
  in ways that have nothing to do with configuration.

  WHAT DOES NOT PERSIST, SPECIFICALLY. "Some settings may not persist" is no use
  to someone who just got an HTTP 200. Until #1091:

    - The GitHub App configuration PUT returns HTTP 200 and does not persist.
      You get a success response and no effect, every time, indefinitely. This
      is the one most likely to cost someone an afternoon.
    - The integration settings writes mostly log a warning and carry on. One of
      them returns HTTP 500 to the caller while the server keeps running.
    - The startup write logs a warning and continues.

  Nothing crashloops, nothing is corrupted, and nothing diverges. Every one of
  these paths is soft by inspection - no log.Fatal, no os.Exit, no panic.

  This is a behaviour change from a writable settings file, and in one respect it
  looks worse: previously these writes succeeded, appeared to work, and were
  silently lost at the next pod replacement. Now they never take effect at all.
  Consistent beats intermittent - a write that always fails visibly is
  debuggable, and a write that works until a rollout is not - but you have to be
  told, which is what this section is for.

  Configure these through your values file and helm upgrade instead. Note the
  separate hazard that a hub which has already run against Postgres keeps some
  settings in database rows that shadow the file entirely; see VALIDATION.md.

ROTATING AN OAUTH CLIENT SECRET REQUIRES A RESTART YOU HAVE TO RUN YOURSELF

  This release sets OAuth client credentials, so this applies to you. A
  helm upgrade that changes the client secret rewrites the settings Secret
  and reports success - and every running pod keeps using the old credential
  until something restarts them. If you rotated because the old secret
  leaked, it is still live at that point.

  The pods do NOT roll automatically. checksum/settings is deliberately
  blind to credential changes: a digest that moves when the credential
  moves is a verification oracle for it, and pod annotations are readable
  by anyone with pod read access. The trade-off is real and is not papered
  over: automatic rotation and zero-knowledge annotation are the same
  requirement with opposite signs. This chart chose zero-knowledge, and
  the cost is one command:

    kubectl rollout restart deploy/{{ include "scion-hub.fullname" . }} -n {{ .Release.Namespace }}

  Expect it to log everyone out. That is the rotation working: the old
  sessions are signed with the old OAuth state, and the new pods do not
  honour them. If nobody is logged out, the old pods are still running.

  What happens if you forget: nothing, visibly, until the provider revokes
  the old client secret. At that point every login fails and the hub looks
  healthy - /readyz passes, the pod is Ready, and Kubernetes reports no
  event. The failure is at the OAuth token exchange, which is an HTTP 401
  from the provider, logged but not surfaced.
{{- end }}

SCHEMA_VERSION IS LOAD-BEARING

  The rendered file carries schema_version: "1", and it is not boilerplate.

  The hub auto-migrates a settings file whose format it cannot detect, the
  detector keys on this field, and the migration replaces the file with
  os.Rename. Renaming over a bind-mounted path returns EBUSY. Every other write
  to this file under the mount is soft; that one is a hard failure. Rendering
  schema_version is what stops the migration from ever being attempted, and the
  hub does not guard the path itself in hosted mode - deliberately, on the
  grounds that the chart controls the input. If you supply your own settings.yaml
  through config.existingSecret, it must carry schema_version.

ACTION REQUIRED: THIS RELEASE'S CLUSTER-SCOPED RBAC OBJECTS HAVE BEEN RENAMED

  Chart versions up to 0.1.0 could give two releases in different namespaces the
  SAME ClusterRole and ClusterRoleBinding name, because the namespace was cut
  off the end by a length limit. Those objects carry cluster-wide secrets
  get/list/create/delete and pods/exec create. This release fixes the naming.

  This release now uses:   {{ $current }}
  It previously used:      {{ $legacy }}

  IF THIS RELEASE HAS BEEN INSTALLED BEFORE, THE OLD OBJECTS STILL EXIST. Helm
  does not delete them on upgrade when you apply rendered manifests, and this
  chart cannot delete them for you. Their permissions remain live.

  DO NOT DELETE THEM YET. The old name is SHARED with every other release that
  was colliding with this one - not necessarily one other release, but every
  release whose namespace was cut to the same text, which can be several. It may
  still be the working ClusterRoleBinding of an install that has not upgraded.
  Deleting it would strip that install's permissions while its pods keep
  running, and nothing in your terminal would tell you a second release was
  affected.

  NO COMMAND BELOW CAN TELL YOU HOW MANY RELEASES SHARE IT. The object records
  which install applied last; it does not record the others, and they leave no
  trace on it. So this is not something the chart knows and you can look up - it
  is not recoverable from the object at all. The only sound check is your own
  inventory of the releases you have installed from this chart.

  DO NOT IDENTIFY IT BY LABEL SELECTOR. This works, which is the problem:

      kubectl get clusterrolebinding -l app.kubernetes.io/instance={{ .Release.Name }}

  returns both the old and the new object, and dropping the new name leaves
  exactly one plausible thing to delete. But every colliding release carries
  IDENTICAL labels - including that one, because the releases collide precisely
  by sharing a name - so the object it hands you may belong to several installs.
  The selector cannot tell you that. It will show you one object either way.

  1. Find out which namespace currently owns the old object. Since the labels
     cannot distinguish the colliding installs, the subject is the only field
     that can:

       kubectl get clusterrolebinding {{ $legacy }} \
         -o jsonpath='{.subjects[0].namespace}'

     If that prints nothing, the object is already gone and you are done.

     THIS TELLS YOU WHO APPLIED LAST. IT DOES NOT TELL YOU WHO ELSE IS USING IT.
     Seeing your own namespace here does not mean you are the only user, and it
     does not by itself make the object safe to delete.

  2. Upgrade every release that shared the old name. Step 1 cannot enumerate
     them for you; work from your own list of installs of this chart. The object
     is an orphan only once every one of them is on this chart version or later.

  3. Then, and only then, delete the BINDING - and only the binding:

       kubectl delete clusterrolebinding {{ $legacy }}

  LEAVE THE ClusterRole OF THE SAME NAME IN PLACE. Do not delete it, now or
  later. A ClusterRole that nothing binds grants nothing, so leaving it costs
  you nothing, and it is the one object here with no safety check available:

    - It has NO field that distinguishes the installs sharing it. Not a
      namespace, not a subject - a ClusterRole has no subjects at all. Its
      labels and its entire rules block are byte-identical for every install of
      this chart, so nothing on it can tell you who else is using it.
    - RUNNING THE STEP 1 COMMAND AGAINST IT PRINTS NOTHING, and that empty
      output does not mean "unused". It means the field does not exist on this
      kind. If you read it as "no subjects, safe to delete", you will revoke
      the cluster-scoped authority of every install still binding it.
    - Recovery is not automatic. roleRef is immutable, so a broken binding
      cannot be repaired by pointing it elsewhere; the ClusterRole has to be
      recreated under the same name.
