  the Filestore phase, which this release does not include.

THE SETTINGS FILE IS READ-ONLY. THIS IS DELIBERATE.

  If you are here because the hub logged a warning about being unable to write
  its settings file, or because a settings change you made through the API did
  not stick: that is this mount, working. Making it writable is the wrong fix,
  and it is the fix everybody reaches for first, so here is the reasoning before
  you spend the evening on it.

  The hub rewrites settings.yaml at runtime. In a Deployment those writes are
  pod-local - the other replicas never see them, and they are lost at pod
  replacement. That alone would only be lossy. What makes it dangerous is
  syncHubSettings, which runs on every boot and re-seeds shared database state
  from the pod-local file for every section whose row is absent or still marked
  as seeded. So a pod that can write this file can promote its own local
  divergence into the shared truth every other replica then reads, at a moment
  nobody chose, with no error anywhere.

  Making the file writable does not fix that. It re-enables it. The proper fix is
  in the hub - the settings file becomes read-only in hosted mode with the
  database as the sole writable store - and it is tracked as ptone/scion#1091.
  When that lands this mount stops being load-bearing. Until then it is the only
  thing preventing the divergence, and the cost of it is a log line.

  Note the directory is NOT read-only. Only the one file is. {{ include "scion-hub.scionDir" . }}
  is the hub's whole state directory - storage/, templates/ and scion-token are
  all created in it - so mounting configuration over the directory breaks the hub
  in ways that have nothing to do with configuration.

  WHAT DOES NOT PERSIST, SPECIFICALLY. "Some settings may not persist" is no use
  to someone who just got an HTTP 200. Until #1091:

    - The GitHub App configuration PUT returns HTTP 200 and does not persist.
      You get a success response and no effect, every time, indefinitely. This
      is the one most likely to cost someone an afternoon.
    - The integration settings writes mostly log a warning and carry on. One of
      them returns HTTP 500 to the caller while the server keeps running.
    - The startup write logs a warning and continues.

  Nothing crashloops, nothing is corrupted, and nothing diverges. Every one of
  these paths is soft by inspection - no log.Fatal, no os.Exit, no panic.

  This is a behaviour change from a writable settings file, and in one respect it
  looks worse: previously these writes succeeded, appeared to work, and were
  silently lost at the next pod replacement. Now they never take effect at all.
  Consistent beats intermittent - a write that always fails visibly is
  debuggable, and a write that works until a rollout is not - but you have to be
  told, which is what this section is for.

  Configure these through your values file and helm upgrade instead. Note the
  separate hazard that a hub which has already run against Postgres keeps some
  settings in database rows that shadow the file entirely; see VALIDATION.md.

SCHEMA_VERSION IS LOAD-BEARING

  The rendered file carries schema_version: "1", and it is not boilerplate.

  The hub auto-migrates a settings file whose format it cannot detect, the
  detector keys on this field, and the migration replaces the file with
  os.Rename. Renaming over a bind-mounted path returns EBUSY. Every other write
  to this file under the mount is soft; that one is a hard failure. Rendering
  schema_version is what stops the migration from ever being attempted, and the
  hub does not guard the path itself in hosted mode - deliberately, on the
  grounds that the chart controls the input. If you supply your own settings.yaml
  through config.existingSecret, it must carry schema_version.

  Schema migration is safe across replicas, but several hub subsystems hold
  state in the pod: the agent control channel manager, the presence manager, the
  port tunnel manager, the local disk attachment store and the in-process event
  bus. An agent's control channel terminates on exactly one pod, so a web
  terminal, log tail, exec or port-forward request that lands on any other pod

  fix this: it pins a client to a pod, not to the pod holding the channel.

ACTION REQUIRED: THIS RELEASE'S CLUSTER-SCOPED RBAC OBJECTS HAVE BEEN RENAMED

  Chart versions up to 0.1.0 could give two releases in different namespaces the
  SAME ClusterRole and ClusterRoleBinding name, because the namespace was cut
  off the end by a length limit. Those objects carry cluster-wide secrets
  get/list/create/delete and pods/exec create. This release fixes the naming.

  This release now uses:   {{ $current }}
  It previously used:      {{ $legacy }}

  IF THIS RELEASE HAS BEEN INSTALLED BEFORE, THE OLD OBJECTS STILL EXIST. Helm
  does not delete them on upgrade when you apply rendered manifests, and this
  chart cannot delete them for you. Their permissions remain live.

  DO NOT DELETE THEM YET. The old name is SHARED with every other release that
  was colliding with this one - not necessarily one other release, but every
  release whose namespace was cut to the same text, which can be several. It may
  still be the working ClusterRoleBinding of an install that has not upgraded.
  Deleting it would strip that install's permissions while its pods keep
  running, and nothing in your terminal would tell you a second release was
  affected.

  NO COMMAND BELOW CAN TELL YOU HOW MANY RELEASES SHARE IT. The object records
  which install applied last; it does not record the others, and they leave no
  trace on it. So this is not something the chart knows and you can look up - it
  is not recoverable from the object at all. The only sound check is your own
  inventory of the releases you have installed from this chart.

  DO NOT IDENTIFY IT BY LABEL SELECTOR. This works, which is the problem:

      kubectl get clusterrolebinding -l app.kubernetes.io/instance={{ .Release.Name }}

  returns both the old and the new object, and dropping the new name leaves
  exactly one plausible thing to delete. But every colliding release carries
  IDENTICAL labels - including that one, because the releases collide precisely
  by sharing a name - so the object it hands you may belong to several installs.
  The selector cannot tell you that. It will show you one object either way.

  1. Find out which namespace currently owns the old object. Since the labels
     cannot distinguish the colliding installs, the subject is the only field
     that can:

       kubectl get clusterrolebinding {{ $legacy }} \
         -o jsonpath='{.subjects[0].namespace}'

     If that prints nothing, the object is already gone and you are done.

     THIS TELLS YOU WHO APPLIED LAST. IT DOES NOT TELL YOU WHO ELSE IS USING IT.
     Seeing your own namespace here does not mean you are the only user, and it
     does not by itself make the object safe to delete.

  2. Upgrade every release that shared the old name. Step 1 cannot enumerate
     them for you; work from your own list of installs of this chart. The object
     is an orphan only once every one of them is on this chart version or later.

  3. Then, and only then, delete the BINDING - and only the binding:

       kubectl delete clusterrolebinding {{ $legacy }}

  LEAVE THE ClusterRole OF THE SAME NAME IN PLACE. Do not delete it, now or
  later. A ClusterRole that nothing binds grants nothing, so leaving it costs
  you nothing, and it is the one object here with no safety check available:

    - It has NO field that distinguishes the installs sharing it. Not a
      namespace, not a subject - a ClusterRole has no subjects at all. Its
      labels and its entire rules block are byte-identical for every install of
      this chart, so nothing on it can tell you who else is using it.
    - RUNNING THE STEP 1 COMMAND AGAINST IT PRINTS NOTHING, and that empty
      output does not mean "unused". It means the field does not exist on this
      kind. If you read it as "no subjects, safe to delete", you will revoke
      the cluster-scoped authority of every install still binding it.
    - Recovery is not automatic. roleRef is immutable, so a broken binding
      cannot be repaired by pointing it elsewhere; the ClusterRole has to be
      recreated under the same name.
