title: Web Dashboard
description: Using the Scion Web Dashboard for visualization and control.
---

The Scion Web Dashboard provides a visual interface for managing your agents, projects, and runtime brokers. It complements the CLI by providing real-time status updates and easier management of complex environments.

## Overview

The dashboard is organized into several key areas:

### Dashboard Home
The landing page provides an overview of your active agents across all projects and the status of your runtime brokers.

### Notifications & Alerts
The dashboard features an integrated notification framework with real-time SSE delivery. 
- **Inbox Tray**: A dedicated tray accessible from the top navigation, providing a centralized view of all persistent messages sent by your agents. It features unread message badges and mark-as-read actions to help you track items requiring human input.
- **Notification Tray**: Provides agent-scoped filtering for status events, accessible directly from the top navigation.
- **Browser Push Notifications**: Opt-in native browser push notifications ensure you receive alerts even when the dashboard is in the background. Default triggers include `stalled` and `error` states, as well as requests for user input.

### Mode Switcher
The header features a **mode switcher** that lets you move between the top-level workspaces: **Dashboard**, **Chat**, and **Terminal**. The header adapts to the viewport width in three tiers:

- **Wide (above 1100 px)**: A segmented mode switcher with text labels and icons, with inline buttons for inbox, notifications, help, theme, profile, and sign-out.
- **Medium (768–1100 px)**: The mode switcher shows icons only. Inbox, notifications, help, theme, profile, and sign-out move into a single account dropdown. A badge dot on the dropdown shows unread messages or notifications.
- **Narrow (below 768 px)**: The mode switcher becomes a dropdown, next to the account dropdown and a hamburger menu.

Inbox and notifications stay reachable at every width. The Terminal entry also shows how many terminal sessions are open.

**Keyboard shortcuts**: Cmd+1, Cmd+2 and Cmd+3 on macOS (Ctrl+1, Ctrl+2 and Ctrl+3 elsewhere) switch to Dashboard, Chat and Terminal. The shortcuts use the physical digit keys, so they are the same on every keyboard layout. They are on by default; turn them off with the **View mode shortcuts** switch on your profile settings page. The setting is stored in the browser.

The web UI also works on phones, down to 320 px wide and in landscape, including notched screens and the on-screen keyboard. Wide code blocks and tables scroll sideways on their own instead of widening the page, and a sideways swipe does not trigger the browser's Back gesture.

### Display Timezone & Clock
The dashboard shows clock times in 24-hour format. The **Display timezone** card on your profile settings page sets the zone used to show times and to read date/time inputs in native chat and scheduling forms. Agent and project lists, relative times, admin and access-boundary views, log viewers, chat, and the file browser all format times in this zone. **Auto**, the default, follows your browser's zone. The value is stored per user as the `timezone` preference (see the [Users API](/scion/reference/api/)). It affects only what you see, never the `TZ` of agent containers. For that, see [Agent timezone](/scion/reference/times-and-timezones/#agent-tz-hub-dispatched-agents).

### Native Web Chat
When enabled via the `web.native_chat` feature flag, the dashboard includes a top-level **Native Web Chat** workspace (a fourth ShellType in the SPA). It offers a rich interface for direct communication and coordination with your running agents and team.
- **Project-Scoped Spaces & Shared Threads**: Conversations are organized into distinct spaces scoped to specific Projects. Within these spaces, users and agents can collaborate on shared discussion threads.
- **Project Context Preservation (Mode Switching)**: When you switch between Dashboard, Chat, and Terminal modes using the header mode switcher, the system maintains your active project context so you do not lose your place:
  - **Dashboard → Chat**: Clicking the **Chat** icon while on a project-scoped dashboard page (e.g., `/projects/:id/...`) takes you straight to that project's chat space (`/chat/space/:id`).
  - **Chat → Dashboard**: Clicking the **Dashboard** icon while in a project chat space (`/chat/space/:id/...` or `/chat/:slug/...`) takes you directly back to that project's detail page (`/projects/:id`).
  - **DMs / General Chat**: If there is no active project context (such as when in Direct Messages or bare `/chat`), the view defaults back to the top-level dashboard `/`.
- **Direct Messages (DMs)**: Start 1-on-1 direct messages covering both human-to-human (H2H) and human-to-agent (H2A) communication, consolidated as a single "global pair" thread per pair.
- **Members Sidebar, Presence & Typing**: A right-hand sidebar displays active project members, showcasing real-time online presence status and typing indicators.
- **Composer Default-Agent Disambiguation**: When sending messages in spaces with multiple active agents, the composer helps resolve which agent is targeted if no explicit mention is used.
- **Attachments**: Upload file or image attachments directly within the composer, with preview tiles rendered instantly on real-time SSE updates.
- **Search**: Built-in chat search lets you query across historical messages and threads.
- **Clickable File Paths**: File paths in chat messages starting with `/workspace/...` or `/scion-volumes/...` automatically render as clickable links, including paths inside inline backtick code spans (fenced code blocks are left untouched). Only file paths are linked, meaning the last segment has an extension or is a known extensionless file such as `Makefile` or `Dockerfile`. Directory paths stay plain text. Clicking these paths opens an on-demand file viewer dialog, fetching the file contents instantly via existing workspace and shared-directory APIs.
- **Chat/Log Switcher**: Instantly toggle between standard conversational chat with the agent and a real-time stream of the agent's raw execution logs inside the same view.
- **Conversation Export**: Export any thread via the export dropdown in the chat header — download as Markdown, print/save as PDF, or copy to clipboard (HTML + plain text). All exported content is HTML-escaped for safe rendering.
- **@-Mentions & Autocomplete**: Call other agents into the thread by typing `@` to trigger a fuzzy-matching, keyboard-navigable agent dropdown. Protected by code-fence guards to prevent triggering inside Markdown code snippets.
- **Visibility Density Filters**: Choose from three filter levels—**Conversation** (pure dialogue), **Verbose** (adds mentions/CCs), or **Full** (adds state updates and background processes)—with preferences saved individually per agent.
- **Layout Density**: Switch between **Dense** and **Comfortable** layout modes via the density toggle to control whitespace and information density across the chat interface.
- **Space Emoji Icons**: Assign optional emoji icons to spaces (stored in project annotations) for quick visual identification in the thread rail.
- **Thread Drag-and-Drop & Collapsible Groups**: Reorder threads in the thread rail by drag-and-drop. Organize threads into named collapsible groups; ordering is persisted server-side via user preferences.
- **Bidirectional Mention Translation**: `@-mentions` are automatically translated between the `@firstname-lastname` format used in the web chat and the `@email` format used by agents, ensuring natural display for each context.
- **Agent-to-Agent Message Expansion**: Background inter-agent communications (displayed in the **Full** density view) are collapsed into a compact pill to preserve screen space. Expanding the pill lists the messages under date dividers (e.g. `Sep 23, 2026`) whenever the day changes. Each message uses a two-line layout: a header with the 24-hour time and `sender → recipient`, above an indented body limited to 2 lines. Truncated messages feature a zoom/expand icon (`arrows-angle-expand`) that opens a rich, full-screen Markdown-rendered dialog overlay showing the message's date and time (e.g. `Sep 23, 14:15`), closeable via its X button or by clicking outside.
- **Scheduled Send** (experimental): With the `web.chat_scheduled_send` [experiment](/scion/reference/experiments/) on (default off), right-clicking **Send** (or long-pressing it on a touch screen) offers **Schedule send**, in topics and direct messages. The Hub holds the message and sends it as you at the chosen time, at least one minute and at most 90 days ahead. Until then only you see it, with a **Cancel** button. The Hub delivers each scheduled message at most once and checks your access again when it sends; a message found more than 60 minutes late is not sent but offered back to you with **Send now**. See [Scheduled Chat Messages](/scion/hosted/user/scheduled-send/).
- **Coherence Sync**: Real-time sync ensures actions taken on external channels (e.g. Discord or Teams) propagate instantly to the Web UI, with delivery state tooltips indicating whether messages succeeded.

### Terminal Workspace
The **Terminal Workspace** (enabled via the `web.terminal_workspace` feature flag, default **ON**) provides a dedicated, multi-pane terminal environment as a top-level workspace alongside Dashboard and Chat. It allows you to manage interactive terminal sessions with your agents in a persistent, multi-pane layout.
- **Multi-Pane Layout**: Open multiple agent terminals side by side. The workspace preserves your active pane layout during navigation and places newly opened terminals into available slots.
- **Shareable Layout URLs**: Multi-pane layouts (the active preset and which agent occupies each pane) are encoded in the page URL. Reloading the page restores the layout, the browser Back and Forward buttons step through layout changes, and you can bookmark or share the URL to reopen the same multi-pane configuration. Single-pane views keep a clean URL. If the layout parameters are malformed or refer to agents that no longer exist, the workspace falls back safely.
- **Session Restore**: The Hub saves your list of open terminals and which one was in front, per user, and restores them the next time you open the Terminal Workspace, including from another browser or device. Only the frontmost terminal connects automatically; the others are restored to the rail and connect when you open them. Agents that have been deleted, or that you can no longer attach to, are dropped from the restored list. If the URL names a specific agent or layout, the URL decides what connects.
- **Jump to Agent (Cmd+K)**: The **Jump to agent** button at the bottom of the Open terminals list, or Cmd+K, opens an agents-only palette. Cmd+K works from anywhere in the Terminal Workspace, including from inside a focused terminal pane. Ctrl+K works too, but only when focus is outside a pane, because inside a pane it is sent to the terminal. Pressing the shortcut again closes the palette. In a single-pane view, picking an agent shows it like a rail click. In a multi-pane layout, the agent fills the next empty pane, or replaces the focused pane when every pane is in use.
- **Cross-Tab Ownership**: Terminal sessions are tracked across browser tabs, preventing conflicts when the same agent is accessed from multiple tabs. A window that does not own the terminals shows **Move terminals to this window**, which moves them from the owning tab to the current window.
- **Reconnect Controls**: If a terminal session is interrupted, the workspace provides reconnect controls to resume where you left off. When a pane drops for a retriable reason, such as a network blip or a brief loss of the Runtime Broker connection, the workspace makes one automatic reconnect attempt the next time that pane is in front, showing a **Reconnecting...** overlay. A clean detach, an ended session, or a missing agent is not retried automatically. Attaching to a stopped agent ends right away instead of waiting to retry. When a stopped or crashed agent is restarted, the pane reconnects on its own once the agent is running again; agents in the `error` phase are treated as stopped. If the automatic attempt fails, use the **Reconnect** button. The **All terminals** toolbar in the open terminals list has two bulk actions: **Reconnect all** connects every terminal that is not connected and whose agent still exists, including terminals restored but not yet opened. **Remove all inactive** (after a confirmation) removes terminals from the list, without affecting the agents: every terminal whose session has dropped or whose agent was deleted, and every restored but not yet opened terminal whose agent is stopped, in the `error` phase, or deleted. Terminals that are connected or still connecting stay, as do restored terminals for agents that are still running. When a button has nothing to act on, it stays focusable and a tooltip explains why.
- **Scoped PTY Cleanup**: When you close a terminal or navigate away, the workspace performs scoped cleanup of its PTY sessions to reclaim resources.
- **Pane Focus**: In multi-pane layouts, the active pane is highlighted with a focus outline. Switching to a single-pane view automatically removes the outline.

### Projects
View and manage your registered projects.
- **Create/Register Project**: The New Project dialog opens with a **Start from** picker:
  - **Blank** (default) asks for a **Workspace Type**: **Git Repository**, **Shared workspace directory** (one Hub-managed directory shared by every agent, the default), **Empty directory per agent** (each agent gets its own private, initially empty directory, with nothing shared and no git repository), or **Local Directory (linked)** (Workstation only). A confirmation dialog appears when you create a project for a git repository that already has one. For how the workspace types map to sharing modes, see [Workspaces & Sharing Modes](/scion/local/workspaces-and-sharing/).
  - **A project template** lists every project created with **Create Template** on a project's detail page, and clones it (see **Clone Project** below). The template's workspace settings are locked and shown in a summary of what is and isn't copied. Secrets, agents, history, and chat integrations are not copied. For a git template you can supply an optional **Git Remote URL** override, and the new project then uses that repository.
- **Clone Project**: Deep-copy settings, labels, environment variables, GCP service account associations, skills, lifecycle hooks, harness configurations, and templates from an existing project to a new project. Cloned service account registrations are marked as unverified to force re-verification on the target project. Built-in defer-driven rollback ensures transactions are atomic and safe. Supports an optional Git remote override so cloned templates and configurations carry over while target users can supply their own repository.
- **Project Settings**: Centralized configuration interface for managing project-scoped environment variables, secrets, and **injected skills**, including "Injection Mode" controls (Always vs. As-Needed). The settings page features a streamlined flow with a "Done" button, hides unnecessary registration options for git-backed projects, and displays Hub-default placeholders for unset configurations. The configuration UI is organized into tabs matching the agent-create form's existing structure, splitting the general settings into:
  - **General**: Template, harness, model, and telemetry settings.
  - **Auth & Security**: Harness authentication, default agent roles, maximum allowed roles, and default project service accounts.
  - **Batch Skill Injection**: Paste a GitHub directory URL (e.g., referencing a folder containing multiple skill subdirectories) into the skill input to trigger directory-discovery. An interactive checkbox dialog allows selecting which skills to add, and submits them as a single atomic batch, with any embedded credentials/userinfo automatically stripped before logging for safety.
- **Workspace & File Management**: Access the comprehensive **inline file editor** to view and modify files directly in the browser, featuring integrated Markdown preview capabilities. The file browser supports **fuzzy and regex-based filtering** for fast navigation. You can also download individual workspace files or generate ZIP archives of entire projects directly from the UI.
- **Template Management**: Direct server-side importing of templates with immediate UI feedback. Includes full template file browsing, editing, and upload capabilities directly within the dashboard. User-scoped templates can be created, cloned, renamed, and inspected via the profile template management UI. An actions dropdown provides streamlined access to template operations, and rename preserves the template's display name, description, and harness configuration.
- **Shared Directory Management**: View and manage project shared directories directly from the Web UI (see [Project Shared Directories](/scion/local/workspace/#5-project-shared-directories)).
- **Agent List & Lineage Views**: See all agents belonging to the project, with options to toggle between card, list, and the interactive **Agent Lineage Graph** view. The agents section is collapsed to a fixed-height, scrollable area by default. Use the expand/collapse toggle to show it at full height. Your choice is remembered in the browser and applies to all projects. In the list view sorted by last update, the Hub sorts the agents server-side: a project with 50 agents or fewer loads in a single request, and a larger project loads one page at a time, with **Prev**/**Next** controls and a page size of 25, 50, or 100. A project with more than 2,000 agents, or a free-text label filter, falls back to the unsorted listing.
  - **Large deployments**: The main **Agents** page and the home dashboard also page through server-sorted results instead of loading every agent. The tree and graph views need the whole set, so they load at most 4 pages of 500 agents and mark the list as capped when there are more. With more than 2,000 agents, the home dashboard shows agent counts only.
  - **Lineage Graph View**: Renders parent/child agent relationships as a zoomable, pannable parent/child forest. Supports a left-to-right horizontal layout option (via a segmented toolbar toggle and `transposeLayout()` helper), custom keyboard shortcuts for fast navigation, updated edge and arrowhead geometry for precise alignment, and collapse pruning for complex trees.
  - **Jump to Agent (Cmd/Ctrl+K)**: On graph views, Cmd+K or Ctrl+K (or the header's palette button) opens an agents-only palette listing the agents the graph currently shows. Picking one expands its collapsed ancestors, then centers, highlights, and focuses its node. Nothing is refetched and no filter changes.
  - **Inline Integration**: The lineage graph is an inline tree/graph component rendered directly in the main agent content slot on both the main Agents page and individual Project detail pages. Filters for agent status and labels apply automatically across card, list, and graph views.

### Agents
Detailed view for individual agents, featuring a high-density tabbed layout and improved breadcrumb navigation with a dedicated back button.
- **Unified Agent Creation**: A unified single-page interface for creating and configuring agents that merges the previous two-phase create/configure flow into a single step (removing the `editingAgentId` round-trip flow).
  - **Primary Fields**: The default visible section features fields for **Name**, **Project**, **Template**, **Harness** (Type), **Broker**, **Profile** (with a native Runtime Profile Selector that dynamically populates available profiles based on the selected broker), **Task**, and **Notify** settings.
  - **Additional Options**: A collapsible area, shared with the Edit page's form, in five tabs:
    - **General**: **Branch** (git projects only), **Model** (a model ID, or pick a size alias), **Thinking level**, **Container image**, **Container user**, **Telemetry**, and **Auto-expose ports** with its port filter and scan interval.
    - **Auth & Security**: **Agent role**, **Message mode**, **Harness authentication** and **GCP Identity**.
    - **Prompts**: **System prompt** and **Agent instructions**.
    - **Limits & Resources**: **Max turns**, **Max model calls**, **Max duration**, and CPU, memory and disk requests and limits.
    - **Environment & Labels**: environment variables and labels.

    The request carries only the options you set; the Hub resolves everything else. A field you leave empty shows, as grey placeholder text, the value it will inherit and where it comes from (the template, the project settings or the Hub defaults), when the page can read it from those settings; otherwise it just says **Inherited**. These placeholders cover the template, the project settings and the Hub's public settings only, not every source the Hub consults. Choices such as Telemetry, Agent role or Harness authentication start blank, meaning inherit (an inherited Agent role is the project default, capped at the project maximum); pick a value to set it, and **Clear** returns a field to its inherited value. **Unlimited** removes a limit and is separate from Clear. A project's telemetry setting overrides the agent's value, so when the project sets it, the Telemetry placeholder says so. The Hub-wide public telemetry setting is not shown as an inherited value, because the Hub does not apply it when it creates an agent. **GCP Identity** starts with no mode chosen (unless the project's default applies), and the hint explains which default the server applies; any pick, including Block, is sent as your choice. When the template sets Kubernetes settings, an **Other inline config** summary lists them read-only.
  - **Form Actions**: **Start** creates the agent and starts it, then opens the agent's page. **Cancel** leaves the form without creating anything. The form has no create-only action; to create an agent without starting it, use `scion create`. If the agent is created but does not start, a toast says so with the reason, and the agent remains in the list.
- **Agent Identity & Roles**: The agent detail page includes an expanded GCP Identity card that displays the service account email and target Google Cloud project for all identity modes. This card also displays a color-coded role badge representing the agent's active authorization tier (`full`, `baseline`, `readonly`, or `none`).
- **Quick-Message Button**: Found on agent details, list, and graph cards. Instantly open an interactive modal dialog to chat with an agent (use `Enter` to send, `Shift+Enter` for a newline), gated by your existing message permissions. When web chat is available, an **Open agent DM** button closes the dialog and opens the agent's direct message in chat, carrying over any text you have not sent yet.
- **Graph Card Terminal Shortcut**: Connect straight to an agent's interactive terminal directly from its card in the graph view via a dedicated, icon-only shortcut button. Gated by attach capability and disabled when the agent is offline.
- **Status Tab**: Real-time view of agent lifecycle (Starting, Thinking, Waiting, etc.), including the `suspended` and `error` phases. Includes **stalled agent detection** to flag agents that are alive but hung (activity `stalled`) and offline detection for agents whose heartbeat has gone silent (activity `offline`). An agent with activity `blocked` (intentionally waiting) is shown as **waiting on others**, and an agent with activity `waiting_for_input` is shown as **waiting on parent**; the API and CLI still report `blocked` and `waiting_for_input`. A crashed agent (non-zero exit) is shown in the `error` phase using structured `ExitCode` and `ExitReason` data for high-fidelity crash detection, and can be restarted from the UI.
- **Logs Tab**: Streamed logs from the agent container via the integrated Cloud Log Viewer.
- **Messages Tab**: A dedicated tab for viewing structured messages sent to and from the agent.
- **Configuration Tab**: Dedicated tab for viewing the applied configuration of the agent, featuring a new telemetry configuration card. If you can manage the agent's lifecycle, the tab also has a **Reincarnate** button that, after a confirmation, stops the agent and re-provisions it with its current configuration (the web counterpart of `scion reincarnate`).
- **Configure Page & Timezone**: The **Configure** button appears in every phase for users who can update the agent. The page's General tab has a **Timezone** row that shows the agent's container timezone and where it comes from. **Pin…** sets an explicit zone and **Unpin** removes it. Each saves immediately, separate from **Save**. Outside the `created` phase the page offers only the Timezone row, and a change applies on the agent's next start. See [Agent timezone](/scion/reference/times-and-timezones/#agent-tz-hub-dispatched-agents).
- **Edit Page (experiment)**: With the `web.agent_edit` [experiment](/scion/reference/experiments/) on, an **Edit** button appears next to **Configure** for users who can update the agent. The Edit page (`/agents/<id>/edit`) edits a `created`, `stopped`, `error` or `suspended` agent's **Model**, **Max turns** and **Max duration**. Each field says when an edit applies (next start, or resume for a suspended agent), shows an unset field's inherited value as a placeholder, and shows a lock with the reason when it cannot be edited; a running agent's fields are locked. **Clear** reverts a field to its inherited value, and **Unlimited** removes a limit. Unlimited on Max duration applies at the next start or resume like any other edit; Clear, and Unlimited on Max turns, reach the agent only at its next reincarnation, which the page says. **Save** sends only the fields you changed. **Save & Start** (or **Save & Resume** for a suspended agent) also starts the agent with the new values. If someone else changed the agent after the page loaded, the save is refused and the page offers **Reload**, keeping your edits.
- **Debug Panel**: A full-height panel providing a real-time stream of SSE events and internal state transitions for advanced troubleshooting and observability.
- **Terminal**: Interactive terminal access to the agent's workspace, featuring full Tmux support. Includes a dedicated terminal toolbar, seamless window switching (agent/shell), automatic window size adjustment, extended key sequence support (like `Shift+Enter`), and modifier-based text selection (`Shift`-drag or `Option`-drag on macOS). For detailed configuration, see [Interactive Sessions with Tmux](/scion/local/tmux/).
- **Workspace Content Previews**: Content preview capabilities for workspace files directly within the UI, allowing you to quickly inspect agent output and project data.
- **Lifecycle Control**: Start, stop, **suspend**, restart, or delete agents from the UI. Suspending an agent preserves its harness session so a later start *continues* the conversation rather than starting fresh, while restarting a crashed (`error`) agent runs a clean session. For an `error` agent you can instead choose **Resume (best effort)**, which asks for confirmation and then tries to continue the interrupted harness session. Includes bulk operations like the "Stop All" button for efficient bulk shutdown of all agents within a project. To reclaim resources, the Hub also **auto-suspends** agents that stay stalled past a grace period; they resume automatically on the next message. See [Agent Lifecycle](/scion/local/agent-lifecycle/).
- **Agent Delete States**: The Hub deletes agents in the background, so a deleted agent stays visible with a **Deleting…** badge until the Hub reports it gone, and the agent detail page then returns to the list. While an agent is deleting, its Start, Stop, Suspend, Resume, and Delete actions are hidden. If the delete fails, the agent shows **Delete failed** (with the reason) or **Delete interrupted** (the Hub stopped working on it), the actions come back, and a banner offers **Retry** and **Force**. **Force** finishes removing the agent even when the Runtime Broker has not confirmed that its container is gone. When the outcome is unknown, or the delete failed while finishing, starting the agent is blocked until you retry or force the delete. A failed-delete badge clears after about 15 minutes.

### Runtime Brokers
Monitor the infrastructure nodes where your agents are executing.
- **Status**: See which brokers are online and their current load.
- **Configuration**: View broker capabilities (Docker, K8s, etc.).
- **Agent Cap**: The **Brokers** page lists each Runtime Broker's running-agent count against its effective `max_agents_per_broker` cap (for example, "7 / 30"), with the cap's source (Runtime Broker setting, entitlement, or hub default) in a tooltip. When an admin has turned off Runtime Broker quota enforcement, the cap is marked **not enforced**.
- **Runtime Broker Settings**: A Runtime Broker's detail page has a **Settings** section for overrides that apply to that Runtime Broker only. **Max concurrent agents** can be left on the inherited default or set to a custom value (`0` means unlimited); the page shows the current count, the effective limit, and where it comes from. Editing requires the `quota.update` permission. See the [Runtime Broker settings API](/scion/reference/api/#broker-settings-apiv1runtime-brokersidsettings).

### Admin Management Suite
Centralized views for managing the Scion infrastructure and access control (available to administrative users). Each admin page and navigation item is shown only to users whose permissions allow that page (from [`GET /api/v1/auth/admin-status`](/scion/reference/api/#auth-apiv1auth)); holding one admin permission does not reveal the rest. On the **Hub Resources** page (`/settings`), the **Secrets** tab is shown only to super-admins. The **Environment Variables** tab needs `hub.env_vars.read`; only super-admins can add, edit or delete Hub-level variables, and other users with that permission see a read-only list without secrets.
- **Users**: View and manage user accounts and roles.
- **Groups**: Create and manage custom membership groups for policy-based authorization.
- **Access Boundaries**: Full-featured admin suite for defining and managing monotonic permission ceilings (AccessConstraints) via a guided authoring workflow, inventory page, and dry-run preview engine.
- **Service Accounts**: Manage and validate registered Google Service Accounts for use with the metadata emulation pipeline.
- **Brokers**: Comprehensive broker detail pages providing a grouped view of all active agents by their respective projects.
- **Health Dashboard**: The **Health** page (`/health`, also `/admin/health`) shows the current state of the whole system, with optional auto-refresh. It is built from the database only, so every Hub replica shows the same page apart from the "this instance" marker. Access requires the `hub.health.read` permission. The header shows the overall status and, when [`monitoring_dashboard_url`](/scion/reference/server-config/) is set, an **Open monitoring dashboard** link. The page has these sections:
  - **Needs attention**: shown first, at full width. It lists the summary's ranked attention items in server order, with the server's message for each. An item about a Runtime Broker, agent or integration links to it. An item about one Hub instance links to its row in the **Hub instances** table.
  - **Hub**: the whole fleet of Hub instances: the fleet status (see [Fleet status](#fleet-status) below), "N of M instances healthy" (live instances only), the version (or `mixed` when live instances run different versions), and every failing check of a live instance, labelled with its instance and linked to its row in the **Hub instances** table. Uptime, per-instance checks and database connection pool figures are in that table, not here. When the Hub's own identity lacks the IAM access it needs to run the [service account assignment check](/scion/hosted/ha/permissions/#hub-identity-access-for-the-assignment-check), this card also shows the remedy and a link to the access it needs.
  - **Dispatch** (beside the Hub card): stuck messages to agents, stuck Runtime Broker dispatches, and Runtime Broker dispatches that failed in the last hour.
  - **Hub instances**: one row per Hub instance (process) with its label, state, version, uptime, last reported status with any failing checks listed under it, its own database connection pool (**DB pool**: connections in use / pool limit, or in use alone when the pool has no limit; hover for idle connections and the total number of waits for a connection since the instance started), the integrations it runs (**Integrations**: the total, then how many are unhealthy, degraded or unknown; hover for every count), and when it was last seen. The serving instance is marked "(this instance)" and listed first among instances in its state. The list is built from the database only, so every Hub replica shows the same list. See [Hub instances in an HA deployment](#hub-instances-in-an-ha-deployment) below.
  - **Runtime brokers**: a compact table with each Runtime Broker's status, runtime, **Health**, workspace storage, running agents and agents needing attention, version, and last heartbeat. The **Health** column comes from the optional self-health report each Runtime Broker sends with its heartbeat. Plugin records are not listed here.
  - **Integrations**: chat plugins with their platform, health, connection state, version, and the Hub instances that run them (**Managed by**, by label), linking to the integrations page. Health is merged across every live Hub instance, so it is the same whichever replica serves the page (see [Integrations across Hub instances](#integrations-across-hub-instances) below). Callers without the `hub.integrations.read` permission see only the counts by health, with no integration names, in this section and in the Hub instances table. Hidden when no plugins are registered.
  - **Agents**: active and total counts, counts by phase, and lists of agents in the `error` phase, crashed, or offline, each linking to the agent.


  One policy sets the overall status of the summary. It is the worst of: the fleet status of the Hub instances (below); `degraded` when a Runtime Broker is not online, reports itself `degraded` or `unhealthy`, or reports an unhealthy NFS workspace share; `degraded` when dispatch has stuck messages or stuck Runtime Broker dispatches; `degraded` when an integration reports unhealthy; `degraded` when at least 5% of agents are in `error` or `crashed`; and `degraded` when the service account assignment check cannot run. A section that could not be read adds a warning but does not change the status. The same policy produces `attention`, a ranked "Needs attention" list in the `GET /api/v1/admin/health/summary` response. Each entry has a `severity` (`critical` or `warning`), a `kind` (`hub_check`, `hub_instance`, `broker_offline`, `broker_degraded`, `broker_nfs`, `integration`, `dispatch` or `agents`), a `subject`, and a fixed, server-written `message`.

  #### Fleet status

  The `hub` section of the summary describes every Hub instance together, from the rows in the `hub_instances` table (see [Hub instances in an HA deployment](#hub-instances-in-an-ha-deployment)). The serving instance runs no check of its own for the summary: no database ping, no plugin call and no connection pool read. Its own checks reach the page through its row, like every other instance's. Only **live** instances count. With `n` live instances, of which `u` report `unhealthy`:

  - no live instance (`n` = 0): `unhealthy`, with the critical item "No hub instance is reporting";
  - more than half unhealthy (2`u` > `n`): `unhealthy`;
  - any live instance `degraded` or `unhealthy`: `degraded`;
  - otherwise `healthy`.

  So one unhealthy instance out of three is `degraded` (a warning), two out of three is `unhealthy`, and a single-instance Hub (including SQLite) that is unhealthy is `unhealthy`. When the fleet is not healthy, the attention list starts with "N of M hub instances healthy". Each failing check of each live instance adds one `hub_check` item about that instance ("Hub check X is not healthy on instance L"). These items are critical only when the fleet status is `unhealthy`, otherwise warnings; critical checks (`database`, `workspace_storage`) are listed first.

  - A **stale** instance is outside the count and does not change the status. For 15 minutes after its last write it adds the warning "Hub instance L stopped reporting".
  - A **stopped** instance (clean shutdown) adds nothing.
  - If the serving instance cannot read the `hub_instances` table, the fleet status is `unknown`, the warning "Hub instance data not available" is added, and the overall status does not change.
  - If the serving instance cannot read the database at all, `GET /api/v1/admin/health/summary` returns HTTP 503 with a fixed message and no partial data, and the page shows "Health data not available (database unreachable from this hub instance)". Such an instance cannot write its own row either, so the other replicas show it as stale.

  The summary's `hub` fields are `status` (the fleet status), `version`, `instance_id` (the serving instance), `connected_brokers`, `active_agents`, `projects`, `instances` (live instances counted by status: `live`, `healthy`, `degraded`, `unhealthy`; null when the table could not be read) and `unhealthy_checks` (each with `instance_id`, `instance_label`, `name` and `value`). Uptime is per instance and is computed by the page from each instance's start time. `/healthz` and `/readyz` are unchanged: they check the process that answers them.

  For rates and per-replica history, see the [Hub monitoring dashboard](/scion/hosted/single-node/hub-monitoring-dashboard/).

  #### Hub instances in an HA deployment

  Every Hub process writes a small row about itself to the `hub_instances` table: once at start, then every 15 seconds (with ±10% jitter). The row holds the instance's label (the pod name; on Cloud Run, the revision and the first 8 characters of the instance ID; otherwise the host name), its version, its start time, its overall status, its checks reduced to fixed values (`healthy`, `degraded`, `unhealthy`, `available`, `unavailable` or `unknown`; a check with any other value is stored as `unknown`, and a check whose name is not 1-64 characters of lower-case letters, digits and `_` is not stored), and its database connection pool (connections in use, idle, the pool limit, and the total waits for a connection). The in-use, idle and wait figures are refreshed on every write, so they are at most one write interval old. The instance's label, version, status, checks and pool figures are kept within 4 KiB together (the instance ID and timestamps are not counted). The Health page shows each instance's own pool from its row; the instance serving the page does not read its own pool separately. A restart is a new process, so it gets a new row; the label shows that two rows belong to the same pod. On a single-node SQLite Hub the table shows the one running instance and that instance's earlier restarts.

  The summary computes each instance's state when it is read:

  - **live**: the instance wrote its row within the last 45 seconds (three write intervals).
  - **stale**: the instance has not written its row for more than 45 seconds. The process stopped without a clean shutdown (for example, it was killed or its node was lost), or it is running but cannot write to the database. A stale instance's status and version are its last report, shown greyed.
  - **stopped**: the instance shut down cleanly. On a graceful shutdown the Hub stops its writer and records the stop time in its row (within a 2-second budget), so the instance shows as stopped at once, greyed, and never as stale. If the stop cannot be recorded in time, the instance shows as stale instead.

  Instances whose last write (or stop) is within the last hour are listed, up to 50. Older rows stay in the table until they are pruned: once an hour, one Hub replica deletes the rows whose last write (or stop) is more than 24 hours old. If a running instance's row is ever deleted, the instance writes it again on its next write, with a new start time. During a rolling upgrade, a Hub replica that predates this table does not appear in the list, and when such a replica serves the page, the Hub instances table is hidden. "Hub instance data not available" means the serving instance could not read the table.

  #### Integrations across Hub instances

  Each Hub instance also writes the health of the chat plugins it runs to its row, on the same 15-second schedule: at most 32 plugins, each with its name, health (`healthy`, `degraded`, `unhealthy` or `unknown`), whether it is connected, and its version. The plugin's own health message and details are never stored. A plugin that does not answer within 2 seconds is stored as `unknown`. These health queries run only in this background write, so opening more Health pages adds no plugin calls; the summary itself queries no plugin.

  The summary merges the reports of the **live** instances for each plugin:

  - **Health** is the worst value any live instance reports. `unknown` never hides a known value, and is shown only when no live instance reports a known one.
  - **Connected** is `yes` only when every instance that reported a known health says connected. An instance whose report is `unknown` (for example, its plugin did not answer in time) does not count, as for health. When no instance reports a known health, **Connected** is `yes` only when every reporting instance says connected.
  - **Version** comes from the most recent report.
  - **Managed by** lists the reporting instances. The `reported_at` field in the API response is the oldest report used.

  A stale or stopped instance's report is never used. A plugin that has a Hub record but that no live instance reports shows as `unknown` with the reason "not run by any running hub instance". If the serving instance cannot read the Hub instance table, plugins with a Hub record show `unknown` with the reason "hub instance data not available". A change in a plugin's health appears on the page after the next write of the instance that runs it (within 15 seconds) plus the next page refresh.

  On Cloud Run, keep CPU always allocated (`--no-cpu-throttling`, which the shipped deploy script sets) so each instance keeps writing its row between requests. With CPU throttling, an idle instance stops writing and shows as stale.
