## GitHub App installation association authorization and refusal logging

GitHub App installation associations are now re-validated on every token mint and refused unless the project's `gitRemote` is on the configured GitHub host, the installation is active and owned by the remote's account, and either an active Hub administrator bound the installation (`PUT /api/v1/projects/{id}/github-installation`, requiring `hub.github_app.update`) or the project creator's user-scope `GITHUB_TOKEN` secret has repository access on GitHub.

- **Existing associations on upgrade:** Associations recorded before authorization enforcement are not migrated and stop yielding tokens (`association_unauthorized`) at their next mint if neither proof holds. Administrators holding `hub.github_app.read` can list all associated projects and see which ones are unauthorized via `GET /api/v1/github-app/installations/association-report` (optional `?refresh=true`).
- **Automation-created projects and binder re-validation:** Projects created by service accounts or creators without a user-scope `GITHUB_TOKEN` cannot be auto-associated by `POST /api/v1/github-app/installations/discover` or webhooks and require an explicit admin binding via `PUT /api/v1/projects/{id}/github-installation`. Admin bindings are re-validated on every token mint—if the binder is deactivated, deleted, or loses `hub.github_app.update` (or the project's remote changes), minting stops until another authorized administrator re-binds the installation.
- **Refusal log volume:** Repeated identical token-mint association refusals for the same project, installation, and reason are now logged once per state change rather than on every broker poll. See [GitHub App Integration — Project Association](/scion/hosted/single-node/auth/#project-association).

## Message schedules now require a live target agent at authoring, resume, and dispatch-changing updates

Creating a one-shot message scheduled event or a recurring message schedule for an agent that does not exist yet (or is deleted, has a payload `agentId` whose `agentName` disagrees with the agent's slug, or is unreadable and not permitted to message — including an unreadable cross-project target while cross-project messaging is disabled) now fails with `404` (`Agent not found`), matching the trigger authoring rule. An unreadable target that the caller *may* message is accepted, and a conflict between the raw `payload` target and the convenience target fields returns `400`. Previously, unresolved or unreadable targets were accepted at authoring and refused only at fire time.

- **Resume and dispatch-changing updates:** Resuming a paused message schedule (`POST .../resume` or `PATCH` with `status: "active"`), or making any dispatch-changing `PATCH` update (changing `payload`, `cronExpr`, `timeZone`, or `eventType`), now fails with `404` when the target no longer resolves or is unreadable and not permitted to message. Re-target the schedule to a live agent via `PATCH` before resuming.
- **Metadata-only updates, pause, and delete:** Name-only `PATCH` edits (which do not bump the authorization revision), pausing, and deleting remain accepted regardless of target state. A readable-but-unauthorized existing target (or a readable cross-project target with cross-project messaging disabled) still returns `403`.
- **Existing schedules:** Stored schedules and scheduled events are not migrated or re-validated on upgrade, and fire-time checks are unchanged. See [Scheduling — Security & Authorization](/scion/hosted/user/scheduling/#security--authorization).

## Scheduled agent dispatch creates owned agents with credentials and environment gathering

At their next fire, `dispatch_agent` recurring schedules and one-shot scheduled events create agents with the revision's recorded principal as owner and ancestry, an agent role from the project and Hub default role ladder (`scion.io/default-agent-role` → `agent_defaults.default_agent_role` → `full` for user principals; the parent agent's role for agent principals, capped by `scion.io/max-agent-role` and the revision's recorded permission ceiling), the project's default agent settings, and `NoAuth: false`.

- **Secrets, environment variables, and gathering:** Unless the resolved role is `none` (including when the payload sets `"noAuth": true`), the Hub resolves environment variables and secrets from Hub storage under the revision principal (via the owner path for user principals and the progeny path for agent principals) and dispatches creation to the Runtime Broker with environment gathering, satisfying `as_needed` entries automatically. If required environment variables remain unsatisfied, the Hub rolls back the failed create (removing Runtime Broker files, revoking the minted agent token, and compensating the agent row) and records the fire as failed with `missing required environment variables (N)`.
- **Narrow permission ceilings and opting into `noAuth: true` (role `none`):** If the revision's recorded permission ceiling admits no usable role in `{full, baseline, readonly}` (for example, a narrow user access token without the `readonly` selectors), the fire fails rather than silently falling back to a credential-less agent, recording `no usable role for the recorded authority; set noAuth: true or re-authorize the schedule`. Setting `"noAuth": true` (via the convenience field on create or by replacing `payload` via `PATCH`, which bumps `authorizationRevision`) selects role `none` (`NoAuth: true`) under any frozen ceiling and delivers no credentials except the git token (`GITHUB_TOKEN`), which may come from the project scope or the owner's user scope, as with an interactive `--no-auth` create; the owner and ancestry are recorded from the revision principal.
- **Existing scheduled agents, legacy token-authored scheduler edges, and user deletion:** Agents created by schedules before this release are not migrated and keep `NoAuth: true` and role `none` (with no `OwnerID`), including across `scion reincarnate`. Existing scheduled agents whose recorded delegation edge was authored with a user access token (role `none`, `NoAuth: true`, no owner) are also recognized as token-recorded scheduler hops at their next start, resume, or restart, so they may receive the `NoAuth` material the hop previously withheld (the project `GITHUB_TOKEN` and plain non-secret environment variables, with no owner-scope material), matching an interactive role-`none` user access token create. Newly dispatched user-owned scheduled agents count as owned agents when deleting a user, just like interactively created agents. See [Scheduling — Security & Authorization](/scion/hosted/user/scheduling/#security--authorization).

## Agents can report `idle`; idle auto-suspend and auto-wake (experimental)

Agents now end each turn with one of `blocked` (waiting on a specific event, including their own background job), `idle` (nothing to do until new work arrives), `task_completed` or `ask_user`. See [Ending a turn: blocked, idle, task_completed](/scion/concepts/#ending-a-turn-blocked-idle-task_completed).

- **`idle` activity (always on).** `sciontool status idle` sets it. Like `blocked`, it is never marked stalled or offline, and a delivered message clears it. `IDLE` is a default notification trigger of the Hub, the CLI and the Web Dashboard.
- **Suspend reasons in the web.** A suspended agent shows its kept activity and suspend reason the way `scion list` does, for example **suspended · completed (idle)** or **suspended (user)**, with a neutral **idle** badge for running idle agents. The agent's SSE status events, compact list rows and chat member entries now carry `suspendReason`.
- **Idle auto-suspend and auto-wake (`lifecycle.idle_suspend`, alpha, off by default).** With the experiment and `server.hub.auto_suspend_idle` on, the Hub suspends agents that have been `idle`, `completed` or `harness_error` for longer than `server.hub.idle_suspend_after` (default `15m`, minimum `5m`), and any message, mention, notification or scheduled message wakes them. Both settings are in **Admin > Server Config**. An idle suspend is made durable: the final write is retried, a suspend that was interrupted (a failed write, a Hub restart, a stop that timed out) is completed by the idle sweep, and one whose stop never lands is abandoned after roughly 11 to 16 minutes so the agent stays reachable. See [Auto-Suspend of Idle Agents](/scion/local/agent-lifecycle/#auto-suspend-of-idle-agents).

## Flat Cloud Run instances require `block_service_account`, enforce native GCP identity, and gain per-broker project defaults

Flat Cloud Run Runtime Broker instances (`server.broker.instances[].runtime_target` with `type: cloudrun`, behind `hub.flat_cloudrun_target`) now always run per-agent GCP identity natively regardless of `hub.cloudrun_native_identity`, and projects gain a per-broker default GCP service account rung (`defaultGCPIdentityServiceAccountIDByBroker`) behind `hub.flat_runtime_brokers`. There is no database schema migration and no downgrade floor bump.

- **Breaking for existing flat `cloudrun` instances: `runtime_target.block_service_account` is now required.** Before upgrading a host with flat `cloudrun` entries in `server.broker.instances`, provision a dedicated customer-managed GCP service account with zero IAM roles (distinct from `runtime_target.service_account`), grant the instance's `credentials_file` principal `roles/iam.serviceAccountUser` (`iam.serviceAccounts.actAs`) on `service_account`, `block_service_account`, and every account in `assignable_service_accounts`, and set `runtime_target.block_service_account`. Entries without `block_service_account` fail validation and are not activated. `scion doctor` verifies `iam.serviceAccounts.actAs` across all configured Cloud Run agent accounts using the instance's `credentials_file` credentials.
- **Existing no-identity flat Cloud Run agents switch to `block_service_account` and report no ambient GCP credentials.** Agents on flat `cloudrun` whose effective GCP identity is unset, `block`, or a confined default `passthrough` now run as `runtime_target.block_service_account` with `SCION_METADATA_MODE=block`, and existing no-identity agents recreate their Cloud Run instance as `block_service_account` on the next start (workspaces and Agent homes remain on NFS). The Hub's credential preflight reports `agentGCPCredentialsAvailable = false` for those modes on flat Cloud Run, so agents whose harness requires Google Cloud credentials (such as Vertex AI) are refused at Hub preflight unless given `assign` (explicitly or via a default rung) or explicit `passthrough`.
- **Per-agent `assign` and explicit `passthrough` on flat Cloud Run.** Optional `runtime_target.assignable_service_accounts` lists up to 64 unique lowercase customer-managed GCP service accounts (excluding `block_service_account`) that `assign` may attach natively (`400` naming `server.broker.instances[<key>].runtime_target.assignable_service_accounts` before any instance or ownership record is created when unlisted); explicit `passthrough` runs the instance natively as `runtime_target.service_account`, which is stored as the flat Cloud Run row's private GCP host pair (refreshed on co-located activation without `HostIdentity` observation or claimed via remote `scion runtime-broker register --instance`; redacted from broker read/list responses and user-facing `403` refusals unless the caller holds `update` on the broker) and authorized for the broker owner, a Hub admin, or a caller in a project with an owner-consented dispatchable provider link (excluding Hub-own embedded host identities), requiring `iam.serviceAccounts.actAs` under `gcp_iam_check_mode: enforce` (or logging `mechanism=check-disabled` with `authPath` when `"off"`; changing `service_account` later on a remote instance requires clearing or API-updating the stored host-SA pair and re-registering). `scion runtime-broker convert --plan` folds legacy `cloudrun.block_service_account` and `cloudrun.assignable_service_accounts` onto `runtime_target`.
- **Per-broker default GCP service accounts (`defaultGCPIdentityServiceAccountIDByBroker`).** With `hub.flat_runtime_brokers` enabled, project admins can set a verified default service account (`assign` mode) per flat Runtime Broker via `scion project identity default set|unset --broker <name|slug|id>`, `PUT /api/v1/projects/{id}/settings`, or **Project Settings > Configuration > Auth & Security > Per Runtime Broker default service accounts** (with `/agents/new` previewing the inherited default when a flat Runtime Broker is selected). The Hub evaluates `explicit > by-broker > project > hub` on flat Runtime Brokers in both interactive creates and scheduled dispatches, attributes default-rung rejections on broker `400` responses, and ignores stored per-broker entries at ladder resolution while `hub.flat_runtime_brokers` is disabled. See [Flat instance runtime target](/scion/reference/server-config/#flat-instance-runtime-target-serverbrokerinstancesruntime_target) and [Per-Broker Default Service Accounts](/scion/hosted/ha/permissions/#per-broker-default-service-accounts).

## Helm releases named `*-scion-hub` are renamed on upgrade unless `fullnameOverride` is set

The `scion-hub` Helm chart (`deploy/helm/scion-hub`) no longer drops the `-scion-hub` suffix when a release name ends in `-scion-hub` (such as `prod-scion-hub`, excluding exact `scion-hub`). Earlier chart versions rendered `<prefix>-scion-hub` under the exact same object names as a sibling `<prefix>` release in the same namespace.

- **Unchanged releases:** releases named `scion-hub`, `scion-hub-*`, infix names such as `my-scion-hub-1`, or names that do not contain `scion-hub` (such as `prod` or `myhub`) keep their existing object names unchanged.
- **Action required before upgrading an existing `*-scion-hub` release:** without `fullnameOverride`, `helm upgrade` deletes and recreates the Deployment, Service, ServiceAccount, Secrets, ConfigMap, and RBAC objects under `<release>-scion-hub`, breaking GKE Workload Identity bindings (`roles/iam.workloadIdentityUser` bound to `ServiceAccount/<release>`), Ingress or Gateway backends targeting `Service/<release>`, and default conduit relay TLS SANs (`<release>-relay.<namespace>.svc`). When no sibling `<prefix>` release shares the namespace, add `fullnameOverride: <release>` to your values file **before** running `helm upgrade` (or rendering GitOps manifests) to keep every object name in place. See [Deploy via Helm — Upgrade impact](/scion/hosted/ha/helm/#upgrade-impact) for both upgrade paths and cluster-scoped RBAC cleanup.

## Versioned documentation site

The documentation site now publishes immutable snapshots for preview and stable release tags (`/scion/<tag>/`) alongside channel aliases (`/scion/stable/`, `/scion/preview/`, `/scion/nightly/`, and `/scion/main/`), with channel and version selectors in the header bar that preserve your current page path when switching versions (falling back to the target version's home page when a page does not exist there) and display a banner when viewing a non-stable version.

## Global catalog writes need the global permissions and the `core` skill scope is retired

Writes on global (hub catalog) skills and templates are now decided only by new global permissions: `skill.create_global` (existing), `skill.update_global` and `skill.delete_global` for skills, and `template.create_global`, `template.update_global` and `template.delete_global` for templates, with matching token scopes (`skill:update_global` and so on, with a colon) on hub tokens only. The plain `skill.update`, `skill.delete` and `template.*` permissions no longer authorize any write on a global record, and owning a global record grants nothing. The `global-catalog-author` role (revision 3) now holds exactly these six permissions, so a non-admin user bound to it can create, publish, update and delete global skills and templates, including from CI with a hub token, without any authority over project- or user-scoped records. There is no transition period.

- **Re-mint tokens that write the global catalog.** Existing user access tokens whose scopes are plain `skill:update`, `skill:delete` or `template:*`, including hub admins' tokens, no longer write global records (`403`). Mint a new hub token with the `*_global` scopes; see [Hub-boundary tokens for global catalog authoring](/scion/hosted/user/personal-access-tokens/#hub-boundary-tokens-for-global-catalog-authoring) for the CI recipe. These scopes are not part of `skill:manage` or `template:manage`.
- **Owners of global skills lose edit and delete unless they hold the role.** The user who created a global skill can no longer update, publish to, deprecate or delete it, or see its draft versions, without `global-catalog-author` or `hub-admin`. Global templates record their creator for audit only; the creator gets no rights from it.
- **`hub-admin` (revision 12)** gains `skill.update_global` and `skill.delete_global` (revision 11) and `template.create_global`, `template.update_global` and `template.delete_global` (revision 12). It does not gain the plain `template.*` permissions, so it still cannot write templates in projects it is not a member of. `super-admin` is at revision 12.
- **Custom roles** that hold plain `template.*`, `skill.update` or `skill.delete` keep their reach over project and user records but lose writes on global records. Add the matching `*_global` permissions to such roles if their holders should keep writing the global catalog.
- **Import and refresh overwrite with `template.create_global`.** Importing into the global catalog, or refreshing a global template from its source, needs only `template.create_global`, also when the template already exists, so that permission can replace an existing global template's files.
- **Global skills on the hub-wide injected list.** Every holder of `skill.update_global` can change the content of a global skill on the Hub's injected list, which reaches every agent. Review that list; see [Global catalog authoring](/scion/hosted/ha/permissions/#global-catalog-authoring).
- `scion skills publish --scope <scope>` now adds the version only to a same-named skill in that scope (the current project's for `project`, the caller's own for `user`), so a global publish never lands on a same-named project or user skill; without `--scope` the lookup is by name only, as before. `scion skills publish --scope global`, `scion templates update --scope global` (or `--global`), and `scion --global templates delete` and `scion --global templates clone` link and look up no project, so they work with a hub token holding no `project:read`, and `templates update` also with `--hub <url>` outside a project. On the web settings page's global **Templates** tab, **Import**, **Clone** and **Refresh All from Source** appear only for users who can create global templates, and **Delete** per template by capability.

**The `core` skill scope is retired.** Skills now have three scopes: `user`, `project` and `global`.

- On upgrade, the Hub turns every `core` skill into a `global` skill. If a global skill with the same slug already exists, the former `core` skill is renamed `<slug>-core` (then `<slug>-core-2`, and so on) and the Hub logs a warning with the old and new names. The skills' files are not moved.
- Stored injection references to `core` skills (the Hub's injected list and project and user injected skills) are rewritten to `skill://scion/global/<slug>`, using the new slug for a renamed skill.
- A skill URI with a `core` scope (`skill://core/<name>`, `skill://scion/core/<name>`) is rejected with an error naming the `global` replacement, and `scope=core` on `GET` and `POST /api/v1/skills` answers `400`, for delegated credentials too. The CLI's `--scope core` is refused.
- Template files that hard-code `skill://core/...` are not rewritten and now fail skill resolution with that error. An existing agent whose stored configuration holds a `core` skill URI keeps running; when its Runtime Broker provisions it again (for example, a start that re-provisions the agent), a required `core` reference fails provisioning with that error, and an optional one is skipped with a warning. Update such references to `skill://scion/global/<name>`, the recommended form.
- A `core` reference that pointed at no skill before the upgrade may now resolve to a global skill of the same name.
- `skill://global/...` and `skill://core/...` now always mean the local Hub's `global` scope (or are rejected), even where a federated skill registry named `global` or `core` is configured. Older binaries still read a `skill://global/<name>` reference as a federated registry named `global`, so a reference written after the upgrade in that form (rather than one the migration rewrote) no longer resolves locally if the Hub is downgraded. Write `skill://scion/global/<name>`.

There is no schema change and no downgrade floor bump. See [Global catalog authoring](/scion/hosted/ha/permissions/#global-catalog-authoring) and [Skills: scopes and resolution order](/scion/local/skills/#scopes-and-resolution-order).

## Switch an existing agent's harness-config

With the server-layer `hub.reincarnate_harness_switch` experiment enabled (alpha,
off by default), `scion reincarnate <agent> --harness <harness-config>` selects a
harness-config while keeping the agent's identity, workspace, branch and Hub
history. It deletes and rebuilds the agent home, including when the name is
unchanged: the old harness session, transcripts, memory edits, installed tools
and dotfile edits are lost. There is no rollback. Run `--dry-run` first to review
the HOME RESET warning and provide a handoff for continuity. Supported runtimes
are Docker, Podman, Apple Container, Cloud Run / Cloud Run Instances and
Kubernetes; agents in worktree-per-agent projects remain unsupported. See
[Switching harness-config](/scion/local/agent-lifecycle/#switching-harness-config)
for requirements and recovery.

## Agents receive their owner's own material only along a recorded delegation chain

Agents created from a user access token, and their descendants, now receive their owner's material only along a recorded delegation chain. At the agent's next create, start, resume or restart, the owner's user secrets and env vars that are not marked for progeny, the owner's user TZ and the `NoAuth` clone token are withheld from any agent whose chain is not recorded to its owner. The owner's user secrets marked for progeny are withheld from any agent whose chain is not recorded, and runtime reads and listings of them are refused (`chain_unrecorded`) for the same agents; a refused read answers as a missing key. An agent with no stored ancestry is no exception: it keeps the owner's shared secrets only when its chain is recorded to the owner. The required-key check before a start and the environment gather treat such a withheld secret as missing, so the gather prompts for it. An agent whose delegation is not recorded cannot clone at start until its owner reclaims it (or re-creates it). This includes agents whose authority another user re-recorded (for example by reincarnating them with `--role`), sub-agents whose ancestry does not start at the owner, and agents whose chain was never recorded. A lower-scope value with the same key still applies. Launch material is no longer inherited by older descendants of token-created agents whose delegation predates this release. There is no transition period.

To restore an affected agent, its owner reincarnates it from a CLI session (`scion reincarnate <agent>`, keeping its role) or re-creates it. `hack/delivery-census` lists affected agents before and after the upgrade, including a `runtime read` section, with the names (never values) of the withheld rows, among them the owner's shared secrets that start withholds; treat its output as operator-only. The Hub logs one warning per agent and site, and counts `scion.hub.user_material.owner_chain` with `outcome=withheld`. Project secrets are not affected. See [Your Own User Values Follow the Agent's Delegation Chain](/scion/hosted/user/secrets/#your-own-user-values-follow-the-agents-delegation-chain).

## Hub-scoped secrets reach agents only as environment secrets

Hub-scoped secrets now reach agents only when their type is `environment`, apart from the telemetry credential file (see below). **Hub-scoped `file` and `variable` secrets are no longer delivered to agents** at create, start, restart or during credential gathering; a Runtime Broker-scoped secret with the same name now applies in place of those file and variable secrets. A Hub-scoped `environment` secret with the `as_needed` mode is not placed in the agent environment at start; it is supplied only when the agent's harness requests that key during credential gathering. The telemetry credential file (`scion-telemetry-gcp-credentials`, type `file`, with a target path whose last two parts are `.scion/telemetry-gcp-credentials.json`) is still delivered. Hub-scoped environment variables, and secrets at User, Project and Runtime Broker scope, are unchanged. Before upgrading, move any Hub-scoped secret that agents need as a file or a variable to Project or User scope. See [Hub-Scoped Secrets](/scion/hosted/user/secrets/#hub-scoped-secrets).

## Kubernetes agent pods no longer mount a Kubernetes API token

Kubernetes agent pods no longer mount a Kubernetes API token. Restart running agents to apply this to them. To list agent pods that still have a token across all namespaces, see [Agent pod identity](/scion/hosted/ha/kubernetes/#agent-pod-identity).

## Runtime Brokers that cannot receive commands are shown as such

A Runtime Broker is online while its heartbeats arrive, but heartbeats do not use the control channel that carries commands to it. A Runtime Broker whose control channel to the Hub was not connected, for example because the Hub's transport check refused it, still looked healthy. Its health now reports `control_channel` as `healthy` (connected) or `unhealthy` (not connected for more than 90 seconds, or refused by the transport check), and nothing while it is starting or reconnecting within those 90 seconds; `unhealthy` marks the broker `degraded`. A Runtime Broker connected to several Hubs tells each Hub only about its own control channel. The Hub's health summary adds the `broker_command_path` item "is online but cannot receive commands", `scion doctor` counts such brokers, and `scion runtime-broker status` prints a `Commands:` line per hub connection and, while the broker is online, for the broker as the Hub sees it. Its former `Connected: yes` line, which only checked that the Hub API answered, is now `Hub API: reachable`. A hub connection is reported `connecting` until its control channel's handshake completes, instead of `connected` at once. Online status and routing are unchanged.

**Before upgrading, check `server.trusted_proxies`.** A Hub whose TLS ends at a proxy on another host, or at a proxy container on a bridge network, must list the proxy's addresses, or remote Runtime Brokers cannot connect. The Admin -> Maintenance `update-binary` and `rebuild-server` operations now print a `==> Settings check` section that lists required settings left unset; it only warns. See the [upgrade checklist](/scion/reference/hub-upgrade-rollback/#upgrade-checklist-settings-to-check-first).

## Agents created from a user access token receive shared secrets and launch material again

An agent created from a user access token now receives your user-scoped secrets shared with progeny (`--allow-progeny`) at create, start, resume, restart and `as_needed` resolution, as an agent created from a sign-in does. Since the start-time user-secret check, such agents started without them, for example without harness credentials or personal tokens ([miller79/scion#202](https://github.com/miller79/scion/issues/202)). The agent-only permissions `secret.deliver`, `env_var.deliver`, `skill_injection.deliver` and `secret.use` are now intrinsic to the agent's token-recorded edge: the token's scopes do not narrow them, and no token scope is added for them ([ptone/scion#6467](https://github.com/ptone/scion/issues/6467); the decision that `secret.use` gets no selector is recorded on [ptone/scion#2340](https://github.com/ptone/scion/issues/2340)). This applies to existing agents at their next start, with no migration. Every other check on each item still applies, and runtime secret reads and the full agent role still need `project:secret:read`, which no token grants.

Project, Hub and Broker launch material for these agents is now admitted by the regular delivery check instead of the `uat_created_no_deliver_mapping` exception, so its `Warn` line (`exception=product_gap`) no longer appears. **Agents created from a user access token, and their sub-agents, now need their creating user to remain a member of the project to receive launch material, as session-created agents already do.** The withheld `Warn` line names the cause, `root user not admitted to the project`. Uses of the intrinsic rule are counted in `scion.hub.authz.uat_intrinsic`. `hack/delivery-census` reports token-created agents (stored against filtered role, how many owner shared secrets the start-time check admits, and those withheld because their creator left the project). Thanks to Anthony Lofton for identifying and verifying the problem and for the test matrix this change ports ([miller79/scion#199](https://github.com/miller79/scion/pull/199)). See [Agents created from a user access token](/scion/hosted/user/secrets/#agents-created-from-a-user-access-token).

## Agent mounts that reach Runtime Broker host files are refused

A Runtime Broker now refuses any agent mount whose host source reaches its own credentials, local settings, identity and state files, plugins or co-located Hub database, read-only or not. This includes any source that contains the Scion global directory, such as `~` or `/`. Inside `~/.scion`, `volumes:` and shared directories may only use workspace, worktree and shared-directory subtrees. Harness auth files and `SCION_DEV_BINARIES` may not come from `~/.scion` at all, and relative bind sources are refused. A refused create or start returns `400` with the code `control_path_mount`, and a broker whose worktree base or NFS mount root reaches these files does not start.

The broker also records each container's binds when it creates it and re-checks running agents. Running Docker and Podman agents created before this release are checked against the binds the runtime reports, and keep running if those are clear. **They are stopped if any bind reaches these files, if a bind source does not exist on the host, or if the container runtime is not reached over a local unix socket or that cannot be determined, including a remote daemon selected through a Docker context or a Podman connection. A remote daemon reached through a local unix socket, such as an SSH-forwarded socket or a socat proxy, is treated as local; this affects only agents created before this release. Running Apple container agents created before this release are always stopped once.** Stopped agents are marked `error`, and their workspaces are kept; start them again. See [Volume Source Restrictions](/scion/reference/orchestrator-settings/#volume-source-restrictions).

## Runtime Brokers on shared project storage must see the share

A Runtime Broker whose `server.project_storage` uses a shared backend reads project configuration and prepares project directories through its own view of the share, at `<mount_root>/<shares[0].id>` (nfs) or `/mnt/<volume_name>` (gke-shared-volume, cloudrun-volume). If that directory (with its `<subpath_root>`) is not there, the Runtime Broker refuses to create agents in shared-storage projects (`503 project_storage_unavailable`) and reports it in its health: `/healthz` shows `project_storage: "unhealthy: share_not_visible (…)"` and the status is `degraded` (readiness is unaffected), and the heartbeat to the Hub reports `project_storage: unhealthy`. The refusal refers to the share's mount point as "its configured mount point", never by its path, and says what to do for that Runtime Broker:

- **Runtime Brokers whose default runtime is Kubernetes or Cloud Run** (including a Runtime Broker co-located in a Cloud Run or Kubernetes Hub) never mount the share themselves. Make it available in the Runtime Broker's container at that path. A Cloud Run Hub's NFS volume at `<mount_root>/<shares[0].id>`, or the Helm `scion-hub` chart with `workspaceStorage.nfs.enabled: true`, already does this. A separate Runtime Broker pod needs the volume added.
- **Other Runtime Brokers:** mount it at that path, or set `server.project_storage.nfs.auto_mount: true`. If `auto_mount` is already on and the mount fails, the refusal says so and points at the NFS server and export and the Runtime Broker log.
- **Check:** list `<path>/<subpath_root>` in the Runtime Broker's container; it shows project IDs.

**Changed status codes and texts.** On a Kubernetes runtime, a create, start or restart that fails because the share is not mounted on the Runtime Broker now gets `503 project_storage_unavailable` with that path-free text, instead of `500 runtime_error` with the generic "Failed to create agent". An async launch reports the same code and text, and the Hub passes the Runtime Broker's `503 project_storage_unavailable` through to the client with its code instead of a `502 runtime_error`; the Hub passes the message on only when it is one of these path-free texts, and otherwise (for example from an older Runtime Broker, whose message named the mount path) answers with a fixed text. The same holds when a message, agent DM or chat message sent with wake resumes a suspended agent, which now answers `503 project_storage_unavailable` instead of `502 runtime_error`, and for the warning of a provision-only create and the error recorded for a reincarnation or move, which carry the code and the filtered text. The `503 nfs_unavailable` refusal of an NFS-backed create no longer includes the share ID, the mount point or the server and export, with or without shared project storage; the Runtime Broker log has them.

## Lifecycle hooks re-check their writer before minting a token

An `http` lifecycle hook with an execution identity now mints its service-account token only if the hook's writer (`createdBy`) still qualifies at that moment. The writer must still be an active user created before the hook, must still hold `hub.lifecycle_hooks.update`, and, when the GCP IAM check is enforced, must still be able to act as the service account. The service account must still be verified and in scope. Before, these were checked only when the hook was written. When a check fails, the request is not sent, and the execution audit records `hook writer no longer authorized` with the failed check, at most once every 10 minutes per hook and cause. **Existing hooks stop authenticating** if their writer was deleted, suspended or demoted, if the writer's email changed, or, with the IAM check enforced, if the writer lost `actAs`. Updating a hook does not change its writer. To restore such a hook, an admin who holds the authority today re-creates it. On a Hub that uses development authentication, every `http` hook fails if the development user's stored email differs from the configured development identity's email. Re-creating does not help there: make the configured email match the stored one, or update the stored email. `webhook` actions are unchanged. See [Lifecycle Hooks](/scion/hosted/ha/lifecycle-hooks/#the-writers-authority-is-re-checked-every-time-a-token-is-minted).

## Templates describe the job, not the environment

A template now describes the agent's **job** (harness config, model, instructions, skills, tools, limits). Its **environment** (image, resources, volumes, Kubernetes settings, telemetry, hub access) comes only from the harness-config, settings and profiles, the hub and the project. See [Settings Precedence](/scion/reference/settings-precedence/#the-model-a-template-describes-the-job-settings-describe-the-environment) and [Agent Configuration](/scion/reference/agent-config/#key-classes).

**Templates and environment keys** ([ptone/scion#4524](https://github.com/ptone/scion/issues/4524), [ptone/scion#4222](https://github.com/ptone/scion/issues/4222)):

- A template's `telemetry`, `hub`, `image`, `resources`, `kubernetes` and `volumes` are ignored with a warning, and the Hub no longer copies a template's image, env or telemetry into agents. `GET /api/v1/admin/validate-resources` lists the affected templates (`templateConfigFindings`). Move these values to the harness-config or settings.
- Template `env:` variables are now a lowest-precedence fallback: each applies only when no other source sets the key. Previously they beat settings harness-config env. Their values are no longer expanded from the broker host's environment. `SCION_*` keys and every env key the harness-config's auth metadata lists are never taken from a template ([ptone/scion#4968](https://github.com/ptone/scion/issues/4968)). Template env is read from the template's current version on every start, so edits take effect on the next start.
- Existing agents: a template env key baked into an agent's stored config with the same value as the template is treated as the fallback from the agent's next start.

**Precedence** ([ptone/scion#4222](https://github.com/ptone/scion/issues/4222), [ptone/scion#4223](https://github.com/ptone/scion/issues/4223), [ptone/scion#4218](https://github.com/ptone/scion/issues/4218), [ptone/scion#4217](https://github.com/ptone/scion/issues/4217)):

- The Hub default model and thinking level apply only when neither the template nor the project sets one. The template beats the Hub default; the project still beats the template.
- Requester telemetry is on/off only. Other inline telemetry fields are ignored with a warning, on every Runtime Broker.
- Project telemetry policy beats `--enable-telemetry` / `--disable-telemetry` and `SCION_TELEMETRY_ENABLED`.
- When a template sets both `harness_config` and `default_harness_config`, `default_harness_config` wins.
- On the Hub, an explicit `harness:` key in a template wins over inferring the harness from the template's name.

**Template API and storage** ([ptone/scion#4223](https://github.com/ptone/scion/issues/4223), [ptone/scion#4222](https://github.com/ptone/scion/issues/4222), [ptone/scion#4221](https://github.com/ptone/scion/issues/4221), [ptone/scion#4217](https://github.com/ptone/scion/issues/4217)):

- The template API rejects `config` (`400 template_config_in_file`) and `image` (`400 template_image_not_supported`) on create and update, and `PUT` updates metadata only. Edit `scion-agent.yaml` instead.
- `GET` on a template returns a new read-only `agentConfig`, the parsed `scion-agent.yaml`.
- Concurrent pushes of the same template: one wins, the other gets `409 template_conflict`, and the CLI retries once.
- Each template's storage moves to a content-addressed layout, once, on its next commit. Unreferenced blobs are garbage-collected after a grace period (24 hours by default, never less than 1 hour).
- Cloning a template whose bundled harness-config has an unusable provisioner fails with `422`.
- The template row's stored `config` and `image` columns are removed. Their values have been ignored since the previous release and listed by the validate report; they are now discarded. The validate report's `stored_config` kind is gone with them ([ptone/scion#4224](https://github.com/ptone/scion/issues/4224)).

**Settings are no longer baked into agents** ([ptone/scion#4241](https://github.com/ptone/scion/issues/4241), [ptone/scion#4561](https://github.com/ptone/scion/issues/4561), [ptone/scion#4222](https://github.com/ptone/scion/issues/4222)):

- Broker settings telemetry and the settings- and profile-derived image, image pull policy, resources and volumes are applied at each start, not persisted in `scion-agent.json`. A settings or profile change takes effect on the agent's next start. Hub `agent_defaults.resources` and the Hub default limits are also applied on every start ([ptone/scion#623](https://github.com/ptone/scion/issues/623)).
- Agents created before this change keep their already-baked values until they are reprovisioned.
- Agents created before ptone/scion#4222 keep a copy of the Hub default telemetry in their stored config until they are reprovisioned. Starting them no longer resends it.
- Agents without recorded create inputs that are reincarnated keep any old template-derived env keys as explicit env, with a warning ([ptone/scion#4224](https://github.com/ptone/scion/issues/4224)).

**Minimum Runtime Broker version and upgrade order** ([ptone/scion#4224](https://github.com/ptone/scion/issues/4224)): the Hub no longer sends telemetry in the old inline form. Runtime Brokers older than the release that introduced the `templateTiers` capability (TS-2a, [ptone/scion#4218](https://github.com/ptone/scion/issues/4218)) keep working but receive no Hub telemetry default and no project telemetry policy; the Hub logs a warning once per such Runtime Broker. **Upgrade all Runtime Brokers to at least that release before upgrading the Hub to this one.** This replaces the earlier advice to upgrade the Hub first. While the Hub is still older, an upgraded Runtime Broker receives Hub `agent_defaults.resources` only at create. It also gets no live template env: the older Hub sends no template identity on start, so the Runtime Broker uses the template version the agent was provisioned from if that version is still in its cache, and otherwise applies no template env, with a start warning.

## `scion templates sync` and `push` accept a directory path

`scion templates sync` and `scion templates push` now also take a template directory path: `.` or `..`, an absolute path, or one that contains a path separator (such as `./name`). The directory is synced as is, and the Hub name defaults to its base name (`--name` overrides it). Agents that share the project workspace see the project's `.scion` directory read-only, so they now edit a template elsewhere in their checkout and sync it by path, for example `scion templates sync ./templates/planner --name planner`. **An argument containing a `/`, and `.` or `..`, is now read relative to the current directory**: before, `sync a/b` looked up `<templates dir>/a/b`, and `sync .` resolved to the templates directory itself. Bare names are looked up as before. See [Templates & Roles](/scion/local/templates/#hub-commands).

## The harness command line uses the Hub-resolved model

The `--model` argument a Runtime Broker passes to the harness now carries the same model as `SCION_MODEL`: the model the Hub resolved (request, then project default, then template, then Hub default), or an explicit `SCION_MODEL` from `--env`. Before, the argument came from the Runtime Broker's own config, so a project or Hub default model could be shown on the agent while codex, gemini-cli or claude ran on the harness-config default. A size alias the Hub could not resolve is now resolved through the harness-config's `model_aliases`, else the harness's built-in alias table, instead of being replaced by the Runtime Broker's own model. `scion create` also gains `--model` and `--thinking-level`, as on `scion start` ([ptone/scion#3914](https://github.com/ptone/scion/issues/3914), [ptone/scion#378](https://github.com/ptone/scion/issues/378)). See [Settings Precedence](/scion/reference/settings-precedence/#b1-harness-configuration-model-thinking-level-and-scalar-limits).

## The web Create Agent form no longer picks a harness config for you

The Create Agent form used to pre-select a harness config (the template's, else the project or Hub default, else `claude`) and always send it, which made it an explicit request value: a project `default_harness_config` could never apply to an agent created from the web, and a template's harness *type* was used as a harness-config name. The form now sends a harness config only when you pick one. Left unset, the Hub applies its own order (project default, then the template's declared `default_harness_config`, then the Hub default), and the picker shows that inherited value as its placeholder ([ptone/scion#3914](https://github.com/ptone/scion/issues/3914)).

## `scion project list` lists projects across hubs

`scion project list` (and `scion projects list`) now lists the projects on all your registered hubs, each with its hub, merged with the project directories on this machine. Use `--hub <hub>` to show one hub and `--refresh` to fetch each logged-in hub's project list. The earlier output, the project directories on this machine with their type, agent count, status and workspace, moved to `scion project list --local`, which keeps that format byte for byte, JSON included. **Scripts that parse `scion project list` should switch to `scion project list --local`.**

## Posting in project chat threads needs `project.chat_post`

Reading a project's chat threads still needs `project.read`. Posting in them, and promoting a direct message with one of the project's agents into a thread, now also needs the new `project.chat_post` permission on the project. The built-in `project-owner`, `project-admin` and `project-member` roles and the `hub-admin` and `super-admin` system roles get it automatically on upgrade, so their holders keep posting. A send without it answers `403 chat_post_denied`, and the web thread shows a read-only notice instead of the message box ([ptone/scion#5518](https://github.com/ptone/scion/issues/5518)). See [Chat posting](/scion/hosted/ha/permissions/#chat-posting). These chat writes do not check `project.chat_post` yet: thread create; thread rename, default-agent change and delete; project attachment upload; message edit and delete; and thread posts sent through the agent message endpoint (`POST /api/v1/agents/{id}/message` with a thread key). They keep their existing checks, and are tracked in [ptone/scion#5519](https://github.com/ptone/scion/issues/5519).

A new token scope, `project:chat_post`, keeps that permission on a user access token so the token can grant roles that include it. A token that grants `project-member`, or any other role that holds `project.chat_post`, through `project:manage` now also needs `project:chat_post`; mint a new token for existing membership automation. Posting by token is unchanged: `inbox:write` on the token and `project.chat_post` on your account.

Upgrade note: **custom project roles are not changed.** A principal whose only access to a project is a custom role that holds `project.read` but not `project.chat_post` can no longer post in that project's threads, and their scheduled chat messages fail with `no_access` when they come due. This is intended: a role that only reads should not post. If such a role should keep posting, an administrator must add `project.chat_post` to it (Role & Binding Management).

## Timezone handling changes

During the week of September 28 ([release notes](/scion/release-notes/2026-09-28/)), timezone handling changed: the Hub sends every timestamp in UTC with `Z`, the web dashboard has a per-user display timezone and a 24-hour clock, and cron schedules are UTC only. The runtime-profile `timezone` setting introduced the week before ([release notes](/scion/release-notes/2026-09-21/)) has been removed: an agent's `TZ` now comes from its pin, `TZ` environment variables on the Hub, or the Hub default timezone. See [Times and Timezones](/scion/reference/times-and-timezones/) for the full behaviour and the operator steps after upgrading. An upgraded SQLite Hub now runs `utc-timestamp-normalize` once at start, after a database snapshot, so no manual step is needed; Admin → Maintenance shows the run as started by `system:hub-start` ([ptone/scion#5194](https://github.com/ptone/scion/issues/5194)).

## Deleted built-in harness configs and templates stay deleted

A deleted built-in harness config (for example `claude`) or the built-in `default` template no longer comes back when the Hub restarts or is upgraded ([ptone/scion#3544](https://github.com/ptone/scion/issues/3544)). This also applies to harness configs left unselected in the setup wizard. The Hub records each built-in it has seeded in the `builtin_resources_seeded` Hub setting, and startup only creates built-ins that are not in that record. Built-ins that are new in a release are still added, and built-ins you keep still receive content updates.

To bring a deleted built-in harness config back, re-import it as a global harness config from its canonical URL, `https://github.com/GoogleCloudPlatform/scion/harnesses/<name>` (for example `.../harnesses/claude`). Use the import box on the **Harness Configs** tab of the Hub's **Settings** page, or `POST /api/v1/resources/import`. On a hosted Hub, a copy imported from any other URL (such as a `/tree/<ref>/` URL), or a re-imported `default` template, is usable but user-managed: it does not receive the content bundled with later releases. Workstation Hubs update it either way. See [Recovering a deleted built-in](/scion/reference/harness-settings/#recovering-a-deleted-built-in).

Upgrade note: on the first start after upgrading, the Hub has no record yet, so built-ins you deleted since the last restart before the upgrade reappear once. Delete them again and they stay deleted.
