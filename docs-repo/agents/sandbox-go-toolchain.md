# Go builds, tests and lint in an agent container

- **Toolchain:** Go 1.26.1 everywhere (`go.mod`, `image-build/core-base/Dockerfile`, CI). `fmt-check` failures are real, often misaligned struct fields: run `make fmt` and confirm the diff is pure alignment.
- **extras modules** (`extras/*`) have their own `go` lines. Each Dockerfile's `golang` image must be at least that version; bump both together (`make check-extras-go-images`).
- **VCS status error** (`exit status 128`) in a worktree: add `-buildvcs=false`.
- **Running code at main's tip:** `main` is checked out elsewhere, so use a detached worktree: `git worktree add --detach /tmp/check <main-sha>`, then `git worktree remove --force /tmp/check`. For single files, `git show main:path`.
- **golangci-lint OOM (exit 137):** `GOGC=40 golangci-lint run --new-from-rev=main --concurrency=1 ./pkg/foo/... ./cmd/...`. `--new-from-rev=main` (or `--new-from-rev=<base-sha>` when local `main` is absent; when `GOCACHE` points at a shared mount such as `/scion-volumes/gocache`, never run `go clean -cache`, and pass `GOCACHE=/tmp/gocache-lint`—or `GOCACHE=/tmp/gocache-<slug>`, removed afterward, on shard builds—if concurrent eviction hits stale export data or missing cache files) shows only issues you introduced. Lint `./pkg/hub` itself in a separate run, as `hack/golangci-lint-split.sh` does in CI: `GOGC=40 golangci-lint run --new-from-rev=main --concurrency=1 --tests=false ./pkg/hub`. Not `./pkg/hub/...`, and not `--tests=false` on a combined run, which would stop linting tests in the other packages. With tests it compiles the whole test package. Its tests then get only `go vet`, through `make vet-hub-shard`. The hub run takes over 10 minutes, and CI lint fails on hub code, so run it in the background when you touch pkg/hub.
- **`make ci` and `make ci-full` compile the whole pkg/hub package** (`lint` runs `go vet ./...` and `test-fast` runs `go test ./...`, both with `-tags no_sqlite`). In a container, run the split CI uses instead: `make fmt-check lint-ci check-custom test-fast-ci build`, plus `make test-cmd-sqlite` when touching `./cmd`, `make test-sqlite-nonhub` (or untagged `go test -buildvcs=false` on the touched package) when touching non-hub `!no_sqlite` packages (`SQLITE_NONHUB_PKGS` in `Makefile`, e.g. `./pkg/store/entadapter/...`, `./pkg/conduit/...`, `./pkg/ent/entc/...`, `./pkg/artifacts/...`), since `test-fast-ci` passes `-tags no_sqlite`, `make test-fixture-coverage` (`./internal/fixturegen/...`, `!no_sqlite`, omitted from both `test-fast-ci` and `test-sqlite-nonhub`) plus `make ent-check` (regenerates `pkg/ent` in place; never run concurrently with builds or tests) when changing `pkg/ent/schema`, and `make tidy-extras` (confirming clean `git diff extras/*/go.{mod,sum}`) plus `make vet-integration-extras` when root `go.mod`/`go.sum` changes or packages imported by `extras/*` (such as `pkg/hub` or `pkg/hubclient`) gain module dependencies (`extras/*` use `replace ../..` with separate `go.sum` files). Cross-package caller guards over `./pkg/hub` live in `./pkg/secret` (`go test -buildvcs=false ./pkg/secret`, `!no_sqlite`, `TestSecretBackendGet_CallersAreHubInternal`—skipped by `test-fast-ci`, so run it untagged when touching `pkg/hub`; `./pkg/util`'s `TestHostGitGoesThroughOneDoor` already runs in `test-fast-ci`). When running targeted hub shards instead of all shards, also check cross-shard lock-ins triggered by your change: for project-page, agent/chat list, or `LayerWeb` experiment response changes, locate and run `TestPerfBudget_AgentEndpoints` (`pkg/hub/perf_budget_test.go`, +1% response-byte budget—prefer opt-in `include=<token>` for bulky per-row fields—and `web/e2e-perf/budgets/fixture-schema.json` parity across `perfBudgetWebRequests`, including `GET /api/v1/experiments` for any experiment with `LayerWeb`; see `docs-site/src/content/docs/contributing/perf-tracing.md`, and in a container refresh via `env SCION_PERF_BUDGET_WRITE_WEB_SCHEMA=1 ./hack/hubshard/shard.sh postgres all "" TestPerfBudget_AgentEndpoints` inside the `unset "${!SCION_@}"` wrapper rather than unsharded `go test ./pkg/hub/`, then update `web/e2e-perf/budgets/fixture.mjs`) and `TestListAgentsLegacy_ResponseBodyMatchesGolden`; for `New()`-registered `requireExperiment` routes, add the experiment to `routeRegistrationExperiments` (`pkg/hub/experiments_helpers_test.go`) and, when it has `LayerWeb`, to the `want` map of `TestResolvedExperiments_WebLayerOnlyFromOneSnapshot` (`pkg/hub/experiments_test.go`), then locate and run that test; and for permission, `UATScope`, or built-in role seed edits (`pkg/hub/permissions/registry.go`, `pkg/hub/seed.go`, `pkg/hub/test_admin_policy.go`), locate and run the lock-ins in `pkg/hub/{permission_registry,seed_roles,uat_project_relationship,test_admin_policy_census,test_admin_a3}_test.go` (under default/SQLite tags so `!no_sqlite` role and relationship tests run; note `web/src/components/shared/token-list.ts` `FALLBACK_SCOPES`, frozen AK1 `AgentScopes` such as `project:read`, and `testAdminPolicyDeny` blocking test-admin group delegation of built-in project roles). When adding `*_Postgres` integration tests in `./pkg/ent/entc/`, `./pkg/testinfra/` or `./cmd/`, also add the pattern to `test-store-postgres-tail` in `Makefile` (explicit `-run` allowlists). SQLite uses a single-writer pool (`MaxOpenConns(1)`), so Postgres row-lock, `SKIP LOCKED` and advisory-lock contention are exercised only against Postgres (CI's T1 Postgres jobs or `SCION_TEST_POSTGRES_DSN` / `SCION_TEST_POSTGRES_URL`); Postgres `TIMESTAMPTZ` also keeps microseconds where SQLite keeps nanoseconds, so a store method that returns an in-memory `time.Now()` which callers compare with a later read must truncate it first (`time.Now().UTC().Truncate(time.Microsecond)`, as `pkg/store/entadapter/message_policy_store.go` does). Then run `make vet-hub-shard SHARD=K`, `make test-hub-shard SHARD=K NOSQLITE=1` (the hub part of `test-fast`) and `make test-hub-shard SHARD=K` for each shard holding a test you touched; new `pkg/hub/*_test.go` files calling SQLite helpers (`*_sqlite_helpers_test.go`) need `//go:build !no_sqlite`, or `make vet-hub-shard` and `NOSQLITE=1` fail. A change to non-test pkg/hub code can break a test in any shard: run every shard (`make test-hub-shards NOSQLITE=1`, `make test-hub-shards`, and `make vet-hub-shard SHARD=K` for each K from `hack/hubshard/hubshard.sh -shards`), or report which shards ran and leave the rest to CI. Report which gates ran. Containers share a cgroup CPU cap (`/sys/fs/cgroup/cpu.max`, often 2 cores regardless of host `nproc`), and some harnesses cap single-command wall time (~7–15m), so pass `-timeout 20m` on large package suites (`./pkg/agent/...`, `./pkg/runtimebroker/...`, `./pkg/store/...`), split `test-fast-ci`, hub lint, and individual hub shards into separate background commands rather than one chained script, and avoid running heavy Go compiles concurrently with `golangci-lint` (which also takes a process lock).
- **pkg/hub tests run in shards.** The whole test package needs about 12 GiB to compile; never build it. `make test-hub-shard SHARD=K` (about 6 GiB; `NOSQLITE=1` for no_sqlite), locate a test with `hack/hubshard/hubshard.sh -locate TestA TestB` (exact top-level names as separate arguments—not a single `"TestA|TestB"` regex or unsplit `$T` in `zsh`; a prefix matches nothing, and one name missing under `-tags` fails the whole call with no stdout). Shards are computed from the current sources, so a test moves when files grow or after a rebase: locate again after editing tests (and separately in a base worktree before compiling a baseline binary), rather than trusting an earlier or briefed shard number, and keep test files unchanged while a shard compiles (its test-list check fails otherwise). For a targeted run, use `./hack/hubshard/shard.sh postgres K "" TestA TestB` (`postgres` is the subcommand name, with separate positional test names; `TAGS` is the build-tag set—`""` runs default/SQLite tags verbosely and `"integration"` runs `-tags integration` Postgres tests; tests gated on `SCION_TEST_POSTGRES_DSN` or `SCION_TEST_POSTGRES_URL` skip, making the script fail, unless that variable is passed inside the env-stripping wrapper, and a missing named test also fails; pass `"all"` instead of `K` to find the shard, and redirect verbose output to `/tmp/<shard>.log 2>&1`), or compile from `hack/hubshard/hubshard.sh -overlay /tmp/ov` with `GOGC=25 go test -buildvcs=false -p 1 -overlay /tmp/ov/overlay.json -tags hubshard,hubshard_K -run ... ./pkg/hub` (or `GOGC=25 go test -buildvcs=false -p 1 -c -overlay /tmp/ov/overlay.json -tags hubshard,hubshard_K -o /tmp/hubK.test ./pkg/hub` to compile once, then run from the package directory as `shard.sh` does: `(cd pkg/hub && PATH="$(go env GOROOT)/bin:$PATH" /tmp/hubK.test -test.paniconexit0 -test.run '^TestA$')`—for `pkg/hub` mutation checks, compile each mutant once with `-c` and run every targeted test from that binary instead of one `shard.sh` call per test, since a compiled binary never reflects later source edits; to check several production-code mutants with one compile, add them all in the scratch worktree before compiling, each behind its own value of an environment variable without the `SCION_` prefix that the env-stripping wrapper removes (`if os.Getenv("MUT") == "m1" { ... }`), run the binary once without it as a control and once per value (`MUT=m1 /tmp/hubK.test ...`), and confirm each value reaches its mutated code, since a surviving mutant may be unreached rather than untested; a mutant in a test file or test double still needs its own compile, and `code-review` (Review Process step 2) owns when mutants may share a build; `-tags hubshard,hubshard_K` without `-overlay` still compiles every test file). Overlays snapshot shard-tagged `_test.go` files (plus generated shard-driver files) only, keyed to that checkout's absolute path—both production `.go` files and common helper `_test.go` files in `./pkg/hub` are read live—so regenerate the overlay after sharded test edits, generate a fresh overlay inside any scratch worktree, and pass caller test names to `-locate` when changing a shared helper. Inject store faults in `pkg/hub` tests with `installStoreFault` / `testServerWithStoreFault` (`pkg/hub/store_fault_helpers_test.go`), never by reassigning `srv.store` (`check-hub-store-reassign`). See `hack/hubshard/README.md`.
- **`-race` on pkg/hub** can OOM under a `ulimit -v` cap. Run targeted tests without `-race`, run `-race` uncapped, or use the nightly Race Detection workflow (`.github/workflows/race-detection.yml`): reporting-only, no_sqlite subset; SQLite-backed tests get race coverage only from an uncapped local run.
- **Leaked `SCION_*` env vars:** an agent container sets dozens (`SCION_PROJECT`, `SCION_CREATOR`, `SCION_MODEL`, …). They affect config, cmd, hub and sync tests, and `SCION_MODEL` fails the hermes provision test in `make ci` (ptone/scion#6260). Strip them all (works in both `bash` and `zsh`, and when none are set): `bash -c 'unset "${!SCION_@}"; exec "$@"' _ make <target>`. That also drops intentional `SCION_*` test settings (`SCION_TEST_POSTGRES_*`, `SCION_PERF_BUDGET_WRITE_WEB_SCHEMA`); pass them inside the inner command (`env SCION_TEST_POSTGRES_DSN=... make <target>`).
- **Gitignored build output fails other gates.** `npm ci` (its postinstall), `npm run build` and Vite create `web/public/shoelace/`, which fails `TestRootLevelStaticFile_ListMatchesPublicDir` (ptone/scion#6979). `make build` (part of `make ci`) creates `build/`, which fails `web/src/utils/ci-web-checks-filter.test.ts` in `npm test`. From the repository root, run `rm -rf web/public/shoelace build` before the other side's gate. Any existing `build/` path counts, so `build/scion` alone is not enough; this also deletes the pinned golangci-lint in `build/tools/`, which `make golangci-lint` rebuilds. Don't run a web build or Vite while `make ci` runs. Don't remove `web/dist`: it holds the tracked `web/dist/client/.gitkeep`.
- **Shallow clones:** a clone-per-agent checkout may be shallow (`git rev-parse --is-shallow-repository`). Then `git diff main...HEAD` and `--new-from-rev=main` find no merge base, or a wrong one. Diff and lint (`--new-from-rev=<base-sha>`) against the base SHA named in your brief, or, where remote use is allowed, `git fetch --deepen=200 origin main` (or `git fetch --unshallow origin main` before full-history `git log -S` / `git blame`).
- **Latest main:** you cannot fetch from a worktree. Once the human has pulled into the primary checkout, `git rebase main` sees it. When fixing a test, check whether it already fails on main (detached worktree) so you fix the current version.
