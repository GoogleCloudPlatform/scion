# Cloud Run native identity, Phase 1 (assign slice)

**Date:** 2026-11-04
**Branch:** scion/opt-f
**Scope:** Phase 1 of the Cloud Run native identity design: the
`hub.cloudrun_native_identity` experiment, the assign path end to end, and
a fail-closed refusal for every other mode while the experiment is on.

## What was built

Runtime layer (commit 1a):

- `pkg/experiments/registry.go`: `CloudRunNativeIdentity =
  "hub.cloudrun_native_identity"` (server layer, alpha, default off, owner
  `cloudrun-runtime`, issue ptone/scion#7374, review by 2027-02-04).
- `pkg/hub/experiments.go`: the hub sends it in
  `HubAgentDefaults.Experiments` while it is on, as it does
  `hub.k8s_nfs_home`. `pkg/hub/test_admin_policy.go` classifies it deny.
- `api.CloudRunIdentity{ServiceAccount, Mode}` and
  `StartOptions.CloudRunIdentity` (`json:"-"`), `RunConfig.CloudRunIdentity`,
  and the `pkg/agent/run.go` wiring beside the Kubernetes identity fields.
  Per dispatch only; nothing persists it.
- `pkg/runtime/cloudrun_runtime.go`:
  - `buildCloudRunInstance`: a non-nil identity sets the instance's
    service account and the `scion-identity` label (first 16 hex
    characters of SHA-256 of the lower-cased account). Nil leaves the
    instance as built from the configured account.
  - `Run` refuses a non-nil identity with an empty account before any
    provisioning or API call (`checkCloudRunIdentity`).
  - Recreate, never restart (`clearExistingForIdentity`, called from
    `reuseOrClearExisting`): with an identity, an existing instance is
    never started, even when its spec matches. This run's own instance is
    deleted run-checked (`instanceOpWith`), its exec key is dropped, and
    Run waits until it is gone (`waitCloudRunInstanceGone`), then issues
    its single `CreateInstance` and waits for the instance to be ready
    (`waitCloudRunInstance`). An instance of another run keeps
    `ErrRunConflict`. An instance without a run label, or a start without
    a run ID, is refused with `ErrRunConflict` naming the agent, and the
    exec key cached for that instance ID is dropped. The identity labels
    are compared and logged as hashes only. Without an identity,
    `reuseOrClearExisting` and `startExistingInstance` keep the upstream
    reuse rules; `StartInstance` is reached only there.

Broker layer (commit 1b):

- `pkg/runtimebroker/gcp_identity_cloudrun.go`: `resolveCloudRunIdentity`,
  called from `buildStartContext` after the Kubernetes identity
  resolution. It returns nil (the configured-account path) unless the dispatch runtime is
  `cloudrun` and the hub sent the experiment.
  - assign: the account comes from `CreateAgentConfig.GCPIdentity.SAEmail`
    on create, or from the resolved env on start and restart. It is
    lower-cased once and must be listed in
    `runtimes.<entry>.cloudrun.assignable_service_accounts` in the broker's
    global settings (new field on `config.CloudRunConfig`, plus the
    schema). A project's own value is ignored with a warning
    (`config.ProjectSettingsHasCloudRunAssignableServiceAccounts`). An
    unlisted account is refused with 400, "account not attachable on this
    broker", naming only the agent.
  - Instance metadata server: the mode env is rewritten to passthrough, with
    `SCION_METADATA_SA_EMAIL` and `SCION_METADATA_PROJECT_ID` kept as
    informational env and no `GCE_METADATA_HOST`/`ROOT` redirect. The
    emulator, its start-up and the env plumbing are untouched.
  - Every other mode (block, unset, explicit, project-default or hub-default
    passthrough) is refused with 400: "... is not yet supported on Cloud
    Run Instances with the hub.cloudrun_native_identity experiment on".
    Phase 2 replaces this.
- `rejectCloudRunIdentityRuntimeChange` at the start and restart late
  resolution sites (see Additions).

## Decisions taken inside the design's latitude

- **Experiment Issue / ReviewBy**: `ptone/scion#7374` and `2027-02-04`,
  as set for this change. No docs-site `experiments.md` row in Phase 1. No test
  or generator requires one; docs follow in Phase 4.
- **Account read on start and restart**: the account is taken from the
  resolved env only when the resolved env itself carries
  `SCION_METADATA_MODE=assign` and `SCION_METADATA_MODE_SOURCE=hub`.
  `effectiveGCPMetadataMode` also honours a source from the agent config
  env. This check is stricter and never looser. Without it the account
  is empty and the dispatch is refused.
- **Gate read on create**: the design reads the experiment from the
  context. On create, `withHubAgentDefaults` is attached only after
  `buildStartContext` (`pkg/runtimebroker/handlers.go` createAgent:
  `buildStartContext` at about :1731, `withHubAgentDefaults` at about
  :1833). So `cloudRunNativeIdentityEnabled` also reads
  `in.Config.HubAgentDefaults`. Both come from the hub's dispatch only.
- **Allow-list location**: on the runtime entry
  (`runtimes.<entry>.cloudrun`, beside `service_account`), selected the
  same way as the Kubernetes mapping (`resolveDispatchProfileSelection`).
  Entries are compared lower-cased and trimmed. A flat instance selects no
  runtime entry, so it allows nothing in Phase 1 (fail closed).
- **Recreate checkpoint**: the delete before the recreate runs behind
  `CheckpointStepPreClean`, so an async launch can still be cancelled
  before anything is deleted.
- **Recreate delete NotFound**: an instance gone by the time of the delete is
  not an error; the create proceeds.
- **Refusal status**: 400 for the mode refusals and the allow-list, without
  an error code. The Kubernetes `identity_not_mapped` code makes the hub
  build its message from details that include the account, which this
  refusal must not echo.

## Instance reuse with the upstream reuse rules

The branch is based on the upstream change that reuses only a matching
instance (ptone/scion#7297): `Run` builds the instance first and starts an
existing one only when it carries this run's label and its args, image,
service account, secret-backed env (values included), env names and
volumes match (`cloudRunSpecDiff`); otherwise it deletes it run-checked and
creates a new one. That match already covers an identity change (the
service account differs) and a staged secret change (the secret-backed env
differs), so for those cases the native identity rule is redundant with it.
The rule is kept: it also recreates a matching instance instead of
starting it, and it refuses an instance without a run label instead of
deleting it. Dropping it would change the design and needs a plan first.

A create that finds the instance present (`AlreadyExists`) adopts it
under the upstream rules (this run's instance, not being deleted, with a
matching spec) only without an identity. With an identity, an instance
holding the ID cannot be shown to have been created by this Run: the
refused create returns no operation (the instance may also be this Run's
own create, retried after it landed). It is not adopted, and Run refuses
with `ErrRunConflict` naming the agent.

With an identity, the delete before the recreate is run-checked and
strict: an instance that has no run label at the delete's own read is
refused with `ErrRunConflict` naming the agent and is not deleted; the
exec key cached for that instance ID is dropped.

## Additions to the design

- **Runtime-change guard**: `rejectCloudRunIdentityRuntimeChange` runs
  beside the Kubernetes checks in `startAgent` and `restartAgent`. It
  refuses with 409, before any side effect, when
  `(opts.CloudRunIdentity != nil) != (late runtime == cloudrun && gate on)`.
  The message names the agent and the runtime change, never an account.
  The existing `rejectRuntimeClassificationMismatch` already refuses any
  early/late runtime-type change on those paths. This guard is defence in
  depth with a specific message, and it keeps holding if that general
  check is ever relaxed. It also refuses a change of Cloud Run profile or
  runtime entry between the two resolutions (the selection the allow-list
  was read from is kept on the start context as `CloudRunSelection`), since
  the allow-list is per runtime entry.
- **Flat instances**: a flat Runtime Broker instance has no allow-list or
  block account setting. With the experiment on, assign and block there
  are refused with their own message naming the agent ("flat Cloud Run
  instances do not support assigned identities yet"), before any settings
  are read. A selection with no runtime entry is refused before the global
  settings are loaded.
- **Allow-list entry format**: entries that are not service account
  emails are reported at Warn where the list is read
  (`config.CloudRunAssignableServiceAccountWarnings`), by position only.
  The schema keeps plain strings; matching stays case-insensitive.
