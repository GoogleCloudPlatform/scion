# Cloud Run native identity, Phase 3 (hub side)

**Date:** 2026-11-04
**Branch:** scion/opt-f-p3 (on scion/opt-f 49ca21cd)
**Scope:** Phase 3 of the Cloud Run native identity design: the broker's
report of its Cloud Run assignable accounts, the hub's "natively assigned"
decision, the agent token scope and GCP token refusal for such agents, and
the hub dispatch precheck for Cloud Run profiles, including brokers whose
report is below version 3.

## What was built

Broker report (commit 1):

- `api.BrokerSAReportVersion` is 3, and `api.BrokerSASourceCloudRunAllowlist`
  is `"cloudrun_allowlist"`.
- `hubclient.ProfileSAMappingsState` has two booleans:
  `CloudRunNativeIdentity` and `CloudRunBlockAccount`.
- `pkg/runtimebroker/sa_mappings_report.go`: `cloudRunProfileSAReport`
  reports each profile whose runtime entry in the broker's global settings
  (global file plus DB overlay, the same source Phase 1 reads) resolves to
  `cloudrun` or `cloudrun-instances`:
  - `cloudrun`: one entry per account in
    `runtimes.<entry>.cloudrun.assignable_service_accounts`, lower-cased,
    trimmed, de-duplicated and sorted. Each entry carries only the GSA, with
    Source `cloudrun_allowlist`. The report is complete, with
    `CloudRunNativeIdentity` true and `CloudRunBlockAccount` set when
    `cloudrun.block_service_account` is non-empty after trimming. The block
    account itself is never sent.
  - `cloudrun-instances`: complete, no entries, no support.
  - ForceRuntime: incomplete (`force_runtime`), no entries, no support.
  - A profile with no runtime entry gets no report.
  - Flat instances send no profile report at all (the heartbeat drops it),
    so no Cloud Run report reaches the hub from one.
- The report hash covers the list and both booleans, so a change to the
  list or to whether a block account is set makes the hub store the new
  report.

Hub (commit 2):

- `store.BrokerProfile` gets the same two booleans (profiles are stored as
  raw JSON, so no migration is needed). `applyProfileSAMappings` stores
  them, compares them, and clears them.
- `pkg/hub/cloudrun_native_identity.go`:
  - `brokerProfileNativelyAssigns` / `agentCloudRunNativelyAssigned`: the
    experiment is on, AND the agent's profile resolves through
    `resolveAgentRuntimeProfileType` to Type `cloudrun`, AND the stored
    report is at version 3 or later with `CloudRunNativeIdentity`. The check
    reads the stored agent record and broker row. With the experiment off it
    reads nothing.
  - `withoutNativeIdentityGCPScopes`, called in `Server.AuthorizeAgentToken`
    (the one grant every agent token mint and refresh goes through), drops
    the GCP token scopes for a natively assigned agent. The broker lookup
    runs only when the candidate scopes include a GCP token scope. A lookup
    error fails the grant (`errMintLookup`).
  - `refuseCloudRunNativeMint` runs in `handleAgentGCPToken` and
    `handleAgentGCPIdentityToken`, right after the standing check. It
    refuses with 403 from the stored record whatever scopes the presented
    token carries, and its message names no account. A lookup error
    refuses with 500. The mint endpoints, the emulator and the
    SCION_METADATA_* plumbing stay in place for every other agent.
- `pkg/hub/gcp_identity_dispatch_precheck.go`: `cloudRunIdentityPrecheck`
  runs at the top of `kubernetesIdentityPrecheck`, so every dispatch path
  (create, create with gather, finalize env, provision, start, restart)
  applies it before any token, run or broker call. It reads the experiment
  from the same dispatch experiment set the broker receives.
  `cloudRunIdentityRefusal`:
  - Report missing or below version 3 (any freshness): every mode is
    refused (`cloudrun_broker_upgrade_required`, "upgrade the broker or turn
    the experiment off").
  - Fresh and complete at version 3: passthrough is refused with "passthrough
    is not available on Cloud Run Instances; assign an account or use
    block". A profile without support refuses assign and block. Assign with
    an account not in the reported list is refused. Block, or an unset mode
    (block on Cloud Run), with no block account reported is refused.
  - Stale or incomplete at version 3: left to the broker.
  - The refusal reuses `identityNotMappedPrecheck` (code
    `identity_not_mapped`, 400, `checkedBy=hub_report`). It adds the
    `CloudRun` reason, `Agent` and `Mode` fields and a `reason` detail.
    The message names the agent, profile and broker and never an account.
    The cross-node dispatch envelope carries the new fields.
- `isKubernetesBrokerProfile` leaves out Cloud Run profiles, so their
  reports never show in the Kubernetes mapping warnings or the per-account
  status view.

## Decisions within the design's latitude

- Scope omission sits in `AuthorizeAgentToken`, not in
  `agentRoleAndScopes`. `agentRoleAndScopes` (httpdispatcher.go:378) is a
  pure function with about twenty callers and no context or store. The GCP
  token scope it lists for an assign agent is taken out at the single grant
  every mint goes through, so no agent token for a natively assigned agent
  carries it.
- The precheck treats both `cloudrun` and `cloudrun-instances` profile types
  as Cloud Run, because the broker runs both through the runtime it calls
  `cloudrun`. Only `cloudrun` can report support, so the "natively assigned"
  decision uses `cloudrun` exactly, as the design states.
- A passthrough the hub default granted (`RequireLocalRuntime`) is decided
  as block, matching the broker's downgrade on Cloud Run.
- The "natively assigned" decision ignores how fresh the report is. A stale
  report that says support exists still withholds the scope and refuses
  mint.
- One error code (`identity_not_mapped`) for every Cloud Run refusal, with
  the reason as a detail, so the existing relay, classification and
  envelope paths carry it as they carry the Kubernetes refusal.

## Report versions per runtime (follow-up commit)

The hub keeps one minimum report version per runtime: the Kubernetes
decision (`profileSAMappingDecisionOn`, behind the dispatch refusal, the
assign picker, the status view and the warnings) requires
`kubernetesSAReportMinVersion` = 2, and the Cloud Run checks require
`cloudRunSAReportMinVersion` = 3. Version 3 adds only Cloud Run reports,
so a version-2 Kubernetes report is decided like a version-3 one, with the
experiment on or off. `api.BrokerSAReportVersion` (3) is what a broker
sends.

## Hub-authoritative native decision (round 2)

The hub alone decides whether a dispatch is native, and the broker runs an
assign dispatch natively only when the hub marked it.

- At every dispatch (create, create with gather, finalize env, provision,
  start, restart), `gcpIdentityPrecheck` runs the Cloud Run checks, the
  Kubernetes check and then `markCloudRunNative`, before any token, run or
  broker call. `markCloudRunNative` decides natively assigned from the
  hub's stored broker row, with the experiment as the dispatch sends it.
  A native decision is recorded on the agent
  (`AgentAppliedConfig.NativeCloudRun`, through the new narrow store write
  `SetAgentNativeCloudRun`, which edits that one JSON key and leaves
  `state_version` alone) and carried on the dispatch context. A broker read
  or record write that fails refuses the dispatch, marked as not sent
  (`errStartRequestNotSent`), so a start claim is released.
- The marker goes to the broker only from that context decision:
  `RemoteGCPIdentityConfig.NativeCloudRun` (`native_cloud_run`) on create,
  and `SCION_METADATA_NATIVE_CLOUDRUN=1` in the resolved env, set in the
  same last step as the hub's metadata mode env and deleted on every
  dispatch that is not native. A stored flag, the agent's config or env, a
  create request or a template never sets it. The key is a reserved env
  target (`SCION_` prefix) and is never persisted from a resolved env.
- GCP tokens (scope at `AuthorizeAgentToken`, both token endpoints, and the
  GCS link source) are withheld when the recorded flag is set or the live
  decision says native. The recorded flag counts whatever the experiment,
  so the token decision for an instance that still runs natively stays the
  same when the experiment is turned off.
- Only a confirmed stop (`DispatchAgentStop` returning nil, direct or
  deferred) or a confirmed delete of every run (`DispatchAgentDelete`)
  removes the flag. A failed clear is logged and leaves it set. A dispatch
  decided non-native keeps it.
- A profile the hub cannot resolve, on a broker that reports native support
  for some profile, is refused at dispatch (`cloudrun_profile_unknown`).
  An agent already running whose profile stops resolving there is natively
  assigned for the token decisions.
- With the experiment on, a Cloud Run dispatch needs a complete version-3
  report confirmed within `profileSAReportFreshFor`. A stale or incomplete
  one refuses every mode (`cloudrun_report_not_current`, "broker report
  stale or broker downgraded").
- An agent config patch (live or held) may not add, change or remove a
  reserved control-plane key (`SCION_*`, `GCE_METADATA_*`, matched by
  `secret.IsReservedEnvTarget`, the helper the env submit and env-secret
  refusals use) in `config.env`. A stored reserved key sent back
  byte-identical passes, because the configure page sends the whole env.
  A held edit that names `env` with a null value clears the env, so it is
  checked as an empty env.
  The native Cloud Run marker is refused whenever it is sent. Dropping a
  stored marker is allowed, since it is the only edit that leaves such an
  env editable. The refusal (400, as the env submit refusal) names the key
  and never its value. The stored env compared is the one the request
  read, and the write is a compare-and-set on that state version, so a
  concurrent change of it makes the write fail. A marker already in a
  stored env is deleted from every dispatch that is not native.
- The SA removal impact view leaves out Cloud Run profiles' entries.
- `kubernetesIdentityPrecheck` keeps its Kubernetes-only meaning, and the
  dispatch paths call `gcpIdentityPrecheck`.

Placement choices in this round:
- The flag sits at the top level of `AgentAppliedConfig`, not inside
  `GCPIdentity`. Identity edits rebuild `GCPIdentity` in many places
  (handlers_agents_core.go, server.go), which would drop the flag outside a
  confirmed stop or delete.
- The record write is a narrow store method modelled on
  `SetAgentRuntimeTarget`, because a versioned write before the broker call
  would conflict with the caller's own later `UpdateAgent`.
- The record is a store invariant (round 3): only `SetAgentNativeCloudRun`
  changes it. Every whole-document write of `applied_config` (`UpdateAgent`
  through `buildAgentUpdate`, and `UpdateAgentConfig`) builds its document
  in `appliedConfigForWrite`. That function reads the row's value (with
  the row lock inside a transaction) and keeps it whatever the caller's
  copy says. The write carries a predicate that applies it only while the
  row still holds that value, so a record landing between the read and
  the write turns the write into a version conflict. Callers that retry on
  a version conflict read the row again. For a stored document that is not
  plain JSON, the condition is its exact text instead.
- One reading of the decision is used everywhere: the top-level key
  spelled exactly `nativeCloudRun` holding the boolean true
  (`rowNativeCloudRun`). SQLite and Postgres read it that way, and every
  Go decode of a stored document (`parseAppliedConfig`, and so `GetAgent`)
  takes the field from that reader, never from the case-insensitive struct
  decode. A test checks that every decode of a stored document into the
  struct sets the field from that reader or is listed as never touching
  it, and fails on a planted decoder without the assignment.
- The role backfill (`BackfillEmptyAgentRoles`, run by the hub's boot
  migration) is an existing writer whose concurrency handling changes. Its
  write of a role-less agent's applied config was unconditional. It is
  conditional on the document it read (`backfillAgentRole`), and it
  re-reads the row up to 5 times when the document changes in between. If
  the document keeps changing, the migration fails with an error naming
  the agent and writes nothing for that agent. Its marker then stays
  unwritten, so the next boot runs the backfill again. For a role-less
  agent with no recorded decision it writes the same document the
  unconditional write produced.
- `CreateAgent` never records the decision. The key edits and the writes
  that start from the row's own document (the launch report, under its
  row lock, and the role backfill, conditional on the document it read)
  carry it through. A test enumerates every `applied_config` writer of the
  store package, so a new one must be classified. This covers the
  reincarnation step and completion writes, the agent PATCH writes and the
  pending-config discard, which all write through `UpdateAgent` or
  `UpdateAgentConfig`. The cost is one extra read of the row per
  whole-document write.
- `markCloudRunNative` writes the record on every native decision, whatever
  the caller's copy says. Any store error refuses the dispatch as not sent,
  with no marker: no row, a soft-deleted row (`ErrNotFound`) and an
  unparsable ID (`ErrInvalidInput`).
- A confirmed stop or delete clears the record only when the caller's copy
  shows it. A copy read before the record leaves it set, so GCP tokens stay
  withheld (fails closed). The remedy is a stop or delete issued through the
  agent's API: that handler reads the agent from the store, so its copy
  shows the record and its confirmed success clears it.
- The resolved env of every create and start request is sealed where the
  dispatcher hands it to the broker transport. `sealMetadataEnv` deletes
  every SCION_METADATA_* key, then writes only the hub's own decision. A
  create takes the mode from its own GCPIdentity config
  (`sealCreateRequest`). A start or restart takes it from the agent's
  applied identity (`sealDispatchMetadataEnv`). The decision covers the
  mode and `SCION_METADATA_MODE_SOURCE=hub`, on start and restart the
  assigned account, project and local-runtime flag, and the
  native marker when this dispatch was decided native. It runs in the four
  send wrappers, which are the only callers of the transport's send
  methods: `sendCreate` (2 sites), `sendCreateWithGather` (9 sites, which
  cover create with gather, provision and its second pass, finalize and
  its second pass), `sendStart` (2 sites) and `sendRestart` (1 site). A
  `go/ast` test enumerates the transport send calls of the hub package and
  fails if a send call does not go through a wrapper. The request builders seal too. As a
  second layer, as-needed env resolution never stores a value under a
  reserved key, including the canonical key an alternative name maps to.

## Dependency on Phase 2

`cloudRunProfileSAReport` reads `config.CloudRunConfig.BlockServiceAccount`,
the field Phase 2 adds (name fixed by the EM). The broker's reading of the
marker and its refusal of an unmarked gate-on Cloud Run assign are Phase 2
work (the shared contract). This branch compiles only once it is rebased
onto Phase 2. Nothing here touches the broker's start-context identity
resolution.

## Known limitations (round 1), addressed

The round-1 open items for an agent the hub could not classify (an
unresolvable profile, ForceRuntime, a profile Type stored as its runtime
key) are addressed by the hub-authoritative marker. The broker runs an
assign natively only when the hub decided native, and the hub withholds
tokens for every agent it marked. The unresolvable-profile refusal and its
mint counterpart close the case where the broker would resolve a profile
the hub cannot see. A broker-recorded applied identity (the broker reporting
back what it applied) stays a follow-up. It would only be needed if the
refusal blocks a case that should be served.

## Open items

- A profile the hub records as Type `cloudrun` but whose runtime entry the
  broker cannot resolve gets no report. With the experiment on, the hub
  refuses it with the upgrade message, although the broker is current. The
  broker would refuse it too.
- A new broker reporting to a hub without this change shows Cloud Run
  profiles as unknown Kubernetes rows in that hub's status views (display
  only; accepted).
- Reincarnation stops the previous instance (a confirmed stop clears the
  record), and the new generation's start records it again. The step and
  completion writes that replace the applied config keep it (store
  invariant; tested).
