# Cloud Run native identity, Phase 2 (block and passthrough)

**Date:** 2026-11-04
**Branch:** scion/opt-f
**Scope:** Phase 2 of the Cloud Run native identity design: GCP identity
mode block on Cloud Run Instances with the `hub.cloudrun_native_identity`
experiment on, the passthrough refusal, and explicit refusals for runtime
entries that cannot carry the identity settings. Phase 1 is in
`2026-11-04-opt-f-phase1.md`.

## What was built

- Setting `runtimes.<entry>.cloudrun.block_service_account`
  (`config.CloudRunConfig.BlockServiceAccount`, schema entry), read from
  the broker's global settings only. A project's own value is ignored with
  a warning (`config.ProjectSettingsHasCloudRunBlockServiceAccount`). It is
  lower-cased and trimmed where it is read. A value that does not match
  the service account email pattern is reported at Warn by setting name
  only (`config.CloudRunBlockServiceAccountWarnings`).
- `resolveCloudRunIdentity` (pkg/runtimebroker/gcp_identity_cloudrun.go):
  - block, an unset mode (block is the default on Cloud Run), a hub-default
    passthrough, and an assign that lacks the hub's marker in the resolved
    env resolve to `CloudRunIdentity{ServiceAccount: <block account>,
    Mode: "block"}`. The metadata emulator stays in block mode as a second
    layer: `buildStartContext` sets the env mode to block for a block
    identity. The selection the block account was read from is kept as
    `CloudRunSelection`, as for assign.
  - With no block account on the selected entry, block is refused with 400
    and a remedy naming the agent and the setting
    (`set runtimes.<entry>.cloudrun.block_service_account on the broker`).
    There is no fallback setting and no use of the runtime's own service
    account.
  - Explicit and project-default passthrough are refused with 400:
    "passthrough is not available on Cloud Run Instances; assign an account
    or use block", with the agent named.
  - A runtime entry whose effective type in the global settings is
    `cloudrun-instances` (its `type:`, else its name, as
    `ResolveRuntime` takes it), or one with only a `cloudrun_instances`
    block, refuses assign and block with a message naming the agent and the
    entry type. No settings field is added for that type. An entry named
    `cloudrun-instances` with `type: cloudrun` carries the identity
    settings like any other. A broker forced to `cloudrun-instances` does
    not select an entry of that name: `forcedRuntime`
    (pkg/runtimebroker/gcp_identity_assign.go:540) and
    `findAuxiliaryRuntimeByType` (pkg/runtimebroker/handlers.go:8214) match
    on `Runtime.Name()`, which is `cloudrun` for both settings types.
  - A mode that is none of assign, block or passthrough is refused.
  - Flat instances keep the Phase 1 refusal of assign and block.
- The interim Phase 1 refusal for block, unset and passthrough is removed;
  no code path returns it.

- Native Cloud Run marker: with the experiment on, a Cloud Run assign
  runs only when the hub marked the dispatch for native Cloud Run identity
  (`cloudRunNativeMarked`): on create the wire field
  `GCPIdentityConfig.NativeCloudRun` (`native_cloud_run`), on start and
  restart `SCION_METADATA_NATIVE_CLOUDRUN=1` in the resolved env together
  with `SCION_METADATA_MODE_SOURCE=hub`. The merged env is never read for
  it, and the key is dropped from the request's config env before that env
  is applied, whether or not the experiment is on. Without the marker the
  dispatch is refused with 400, naming the agent only, before any side
  effect. Block, unset and the other modes do not use the marker.
  Ordering: the check requires the hub to write the marker key (the create
  field, or the resolved env key) when it decides native and to delete the
  resolved env key otherwise, since the hub's resolved env can also carry
  the agent's stored config env. That hub change is part of the hub-side
  work; Phase 2 does not land, and the experiment is not turned on, ahead
  of it. The create field is read only on a create, and on a start or
  restart the mode and the account also come only from the resolved env.

## Decisions

- **Hub-default passthrough is mapped to block in the resolver.**
  `downgradeUnverifiedHubDefaultPassthrough` turns a hub-default passthrough
  into block on Cloud Run, but it runs at
  pkg/runtimebroker/start_context.go:1427 (at the Phase 1 head), after
  `resolveCloudRunIdentity` (:597). At resolver time such a dispatch still
  carries mode passthrough with the RequireLocalRuntime flag. The resolver
  receives that flag and treats the dispatch as block, so it gets the block
  account and not the passthrough refusal. `buildStartContext` computes the
  flag once with `hubDefaultPassthrough` (on a create, the create
  request's GCPIdentity when present; otherwise, and on every start or
  restart, the resolved env overridden by the config env) and passes the
  same value to the resolver and to the env re-stamp, so the two readings
  cannot drift apart.
- **Pinned runtime on restart.** `restartAgent` resolves its runtime with
  `resolveExistingAgentManager(runtimeOpts, ..., pin)`
  (pkg/runtimebroker/handlers.go:5365 at the Phase 1 head). With an empty
  `runtimeOpts.Profile`, a pin and no forced runtime it returns the runtime
  the agent's container was found on (:7731-7734), while the allow-list and
  block account were selected through settings
  (`resolveDispatchProfileSelection`). Two Cloud Run entries both report
  the runtime type `cloudrun`, so the type check alone cannot tell them
  apart. The late check therefore also compares the pinned runtime's
  recorded global entry (`RuntimeBuildRecord.EntryName`) with
  `CloudRunSelection` and refuses with 409, before the agent is stopped,
  when they differ or the pin records no entry. The pin condition moved
  into `existingAgentUsesPin`, shared by `resolveExistingAgentManager` and
  `pinnedCloudRunEntry`, so the two cannot drift. `startAgent` resolves
  through settings only (handlers.go:4096) and passes no pinned entry. A
  pin that records no entry is refused with the remedy "recreate the agent
  or restart it with its saved profile".
- **Malformed block account.** A non-matching block account value is still
  used, as configured; the instance create then fails. Only the warning is
  added, matching the allow-list entries.
- **Allow-list docstring.** `CloudRunAssignableServiceAccountWarnings`
  states that a non-service-account entry still matches an equal assigned
  value at the broker and that the instance create then fails.
