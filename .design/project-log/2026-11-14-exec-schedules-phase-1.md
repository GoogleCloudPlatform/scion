# Exec schedules Phase 1: one-shot exec events (API only)

**Date:** 2026-11-14
**Branch:** scion/exec-schedules-1 (stacked on scion/exec-schedules-b, ptone/scion#7921, at fc05a00b; itself on scion/exec-schedules-a, ptone/scion#7916)
**Issue:** ptone/scion#7883 (Phase 1 of ptone/scion#7818)
**Design of record:** scratchpad `projects/exec-schedules/design/design.md` (AGREED, D1-D11), "Implementation Phases" -> Phase 1.

## What this branch adds

- **Storage** (as of round 2): additive Ent table `scheduled_exec_runs`. It has its own UUID `id` and a unique `event_id` that is a foreign key to `scheduled_events` with `ON DELETE CASCADE`: a run cannot exist without its event, every hard delete of an event removes its run, and the purge and project deletion also delete runs first in the same transaction. `last_polled_at` drives the sweeper's rotation. `ScheduledExecRunStore` provides: insert; mark running; a compare-and-set finish (`finished_at IS NULL`, first writer wins) that writes the event in the same transaction, only while it is still `fired` or `expired`; the expired-lease list; the least-recently-polled claim; a by-event lookup for responses; the unadmitted-event list and conditional fail (P2-R1); and the quota-checked event insert. New scheduled-event status `skipped` (the status column is a free string, so no enum migration). `ListScheduledEvents` now pages with a `(created, id)` keyset token (P2-R2). No destructive change, so no downgrade-floor bump.
- **Authoring** (`handlers_scheduled_exec.go`, `authorize_scheduled_exec.go`): `eventType: "exec"` on `POST /scheduled-events` with `agentId`/`agentName`, `command`, `timeoutSeconds` (or a raw `payload`). It is answered like an unknown type unless `hub.exec_schedules` and `hub.conduit` are both on. The payload is decoded strictly and checked against the bounds again at fire time. The target must exist in the project. Authorization is `agent.attach` through `authorizeAgentTargetAction`, the live `/exec` rule; an unreadable target answers 404, so there is no existence oracle. Managed runtimes get 422. Quotas are 20 per target and 200 per project (pending one-shot events; recurring joins in Phase 2) and answer 429. A per-principal rate limiter allows 1/s with a burst of 10. `/schedules` and `/scheduled-events` create and PATCH bodies are limited to 64 KiB.
- **Fire** (`scheduled_exec_fire.go`): flag check, then the 10-minute missed window, then `authorizeScheduledExecFire` (revision liveness and admission, the target by stored id only, the frozen ceiling allows `agent.attach`, the live attach rule, standing). Then preflight: running, not managed, not reincarnating. Then admission: the tracked-run bound (500, never waits) and the shutdown gate. The run row is inserted, then one `exec-start` goes through the launch-pinned client. A detached tracker starts only after `fireEvent` has recorded the event; this is the new `afterScheduledRecord` hook, so the tracker never races that write. The singleton sweeper runs every minute under its own advisory lock. It polls unfinished runs no local tracker owns, in bounded pages with 32 calls in flight, round-robin across agents, and abandons runs past their lease. Shutdown cancels trackers without recording anything, so the sweeper records the real outcome after a restart.
- **Generic `scheduledSkip`** sentinel in `scheduler.go`: `fireEvent` records `skipped` with the reason (not a failure).
- **AC18 hub gate**: `StartAgentExecRun` refuses (`ErrExecSchedulesDisabled`, nothing sent) unless both flags are on and conduit is served. `callAgentControlPinned` no longer checks `conduitRoutable`, so `AgentExecRunStatus` keeps recovering admitted runs after either flag is turned off. Launch pinning is unchanged.
- **Fail-closed serializer** (`scheduled_response.go`): every handler that writes a schedule or scheduled-event body (create, list, get, history, PATCH, pause, resume and `/admin/scheduler`) builds DTOs here. Exec argv is redacted to `{agentId, agentName, timeoutSeconds, commandRedacted, argc, commandSha256}` unless the caller's current credential holds live `agent.attach` on the target; the creator is not exempt. The admin view never reveals argv. `execSummary` (outcome, exit code, duration, output bytes, times) goes to every reader. List envelopes keep `scope`; only their element types changed.
- **Audit** (`scheduled_exec_audit.go`): `schedule.exec.create`, `delete`, `refused`, `skipped`, `admit` and `outcome` through the AuditLogger, with a slog fallback. Records are content-free: argv0 basename (sanitized, at most 64 bytes), `shell_form`, digest and argc only.
- **authzop**: `schedule.event.fire` gains `fireEvent:exec` and the two exec routes as internal-only call sites.

## Decisions taken while implementing

- **Held target**: `failed` with `exec refused` and a `schedule.exec.refused` audit record. `scheduledFireStanding` checks it inside `authorizeScheduledExecFire`, as for scheduled messages: a hold is a moderation refusal, not a not-running case. exec-schedules-arch confirmed this and corrected AC 4 and the D4 preflight list in design.md, which had listed held under skipped.
- **Unknown-start bound**: a run never seen running whose `exec-status` is 404 is definitive after `started_at + 30 s (call) + 60 s (not_after) + 10 s (tolerance) + 10 s`. The hub cannot read the exact `not_after` that `StartAgentExecRun` set, so the call timeout is added as margin.
- **Recurring exec** stays rejected at authoring (Phase 2). A stored recurring exec event that ever reaches the handler fails with a fixed text.
- Quotas count pending one-shot exec events only. Phase 2 adds active recurring exec schedules.
- Fire-time "relationship removed" is tested by removing the creator's project membership. The owner relationship requires active project access, and `UpdateAgent` does not persist owner changes.

## Limits

- No Postgres run here (no Postgres environment in the agent container); the store code uses only portable predicates.
- Daemonized descendants escape the process group (SEC-P4); revocation does not cancel an admitted run (F8).
- `AuditLogger` emission is best effort; the durable record is the run row (SEC-P6, F9).

## Review round 1

Reviewer exec-schedules-1-rev (pass 1, head 4cdb2852): 5 Required, all reproduced, and 1 FYI. All are fixed in this round, with regression tests.

- **R1, the fire overwrote another replica's outcome.** Once the run row exists, the exec fire records every outcome itself, through the run's compare-and-set. The event is written in the same transaction, and only while it is still `fired`/`expired`. The fire then returns `outcomeRecorded`, so `fireEvent` writes nothing after it. The tracker, sweeper and initial fire share that one write path, and the purge deletes. Tests: the reviewer's repro (`TestScheduledExecR1_SweepBeforeFireRecord`), and `TestScheduledExecR1R2R3_InterleavingMatrix`. The matrix runs another replica's poll or expired-lease sweep, a purge, a flag flip and a target deletion at both the admitted and started stages of a fire, for exit 0 and non-zero. It checks four invariants: exec-start at most once; never `fired` with a failed run; the run recorded, or gone with its event; no tracker left behind.
- **R2, the sweep cursor reset.** Each sweep first abandons expired leases, with no status call. It then claims live runs least recently polled first, using a new persisted `last_polled_at` (`FOR UPDATE SKIP LOCKED` on Postgres), in chunks of the in-flight cap. Progress therefore survives deadline exits and replica changes, and fairness covers the whole set. Tests: the reviewer's repro (`TestScheduledExecR2_SweepCursorProgress`), `TestScheduledExecR2_UnavailablePrefixRotates` (7 unavailable runs against a budget of 2 per sweep), and the store test `TestScheduledExecRun_ExpiredAndPollRotation`.
- **R3, the status call used up the write deadline.** Each write now gets its own bounded context, created after the status call returns. `finishScheduledExecRun` returns `(won, err)`: a failed write keeps the run tracked and retried, while an already finished or purged run is done. Tests: the reviewer's repro (`TestScheduledExecR3_SlowStatusOutcomeRecorded`, an 11 s answer) and `TestScheduledExecR3_FailedWriteKeepsTracking`.
- **R4, concurrent authors exceeded the quota.** `CreateScheduledEventChecked` reads the project's pending events of that type and inserts in one transaction. On Postgres it first takes a per-project `pg_advisory_xact_lock` (`LockScheduledEventQuota`); SQLite serializes writers. The losing request gets 429 `quota_exceeded`. Exec create is the only path that adds a pending exec event in Phase 1. Tests: the reviewer's repro (`TestScheduledExecR4_ConcurrentLastSlot`) and the store test `TestCreateScheduledEventChecked_LastSlot` (8 concurrent writers, 1 slot).
- **R5, project deletion leaked run rows.** `event_id` is now a foreign key to `scheduled_events` with `ON DELETE CASCADE`, so a run cannot be inserted for an event that is gone, and every hard delete of an event removes its run. `DeleteSchedulesByProject` deletes runs, events and schedules in one transaction. Schedule deletion does not hard-delete events. The schema is unreleased, so the run table changed in place: a separate `id`, plus a unique `event_id`. Tests: `TestDeleteSchedulesByProject_RemovesExecRuns` (finished and unfinished runs, no insert after delete) and `TestScheduledExecRun_EventForeignKey`.
- **F1, target cleanup read only one page.** `cancelScheduledEventsForAgent` follows `NextCursor`. Test: `TestScheduledExecF1_TargetDeletionCancelsBeyondFirstPage` (1100 pending events).
- A race-detector run then found that tests changed the timing seams while trackers were still reading them. Those reads now go through `scheduledExecSeamMu`.

## Review round 2

R1-R5 and S1 were verified. Round 2 found:

- **P2-R1 (Required, AC10), a crash between the claim and the run insert.** If the hub stops after claiming an exec event (fired, or expired on a restart replay) and before inserting its run, neither the replay (the event is no longer pending) nor the run sweep (there is no run) finishes it. Each sweep now first runs `recoverUnadmittedExecEvents`. It finds exec events claimed more than `scheduledExecAdmitWindow` ago (handler timeout + record timeout + 1 min) that have no run, and records them `failed` with "hub restarted before dispatch". The write is conditional on the event still having no run, in one transaction; for a recurring event (Phase 2) it also records the schedule's failed run. Nothing was ever sent for such an event, because exec-start follows the run insert, and recovery never sends exec-start. Tests: `TestScheduledExecP2R1_ClaimBeforeRunCrash` (the reviewer's repro, for fired and expired claims; checks no exec-start was sent and a claim inside the window is left alone) and the store test `TestUnadmittedScheduledEvents`.
- **P2-R2 (Required, AC11), the F1 fix was incomplete.** The generic `ListScheduledEvents` ordered by `created DESC` but continued with an `id <` cursor, so traversals skipped rows whenever UUID order disagreed with creation order. It now uses the same `(created, id)` keyset token and lexicographic predicate as `ListSchedules`, with the no-progress guard and the 200-row cap; a bare-id cursor is refused as `invalid_cursor`. This fixes every caller: target cleanup, the `/scheduled-events` list and `/schedules/{id}/history`. The quota pre-check and `/admin/scheduler` read a single page and are not traversals. Tests: `TestListScheduledEvents_KeysetTraversal` (the reviewer's fixture: 1001 events, page cap, no duplicates, the old target visited, a bare-id cursor refused) and `TestScheduledExecF1_TargetDeletionCancelsBeyondFirstPage` (same fixture through the hub; asserts the event is cancelled).
- **P2-N1**: storage overview above updated.

## Review round 3

P2-R1 and P2-R2 were verified. ptone decided Q6 = (a), fix P3-R1 and P3-R2, and Q7 = (a), P3-R3 is a documented limitation.

- **P3-R1 (Required), a delayed fire could start a run that was already terminal.** Each run now persists a frozen start deadline, `not_after` (admission + `ExecNotAfter`), and the fire sends exactly that deadline: `StartAgentExecRun` no longer refreshes a deadline the caller sets. Before sending, the fire re-reads the run. It sends nothing if the run is finished, which means recovery or a purge won, and records `start expired` if the deadline has passed. A pause between that check and the send cannot start the command late, because sciontool refuses a start received after `not_after` + tolerance. Recovery's "definitely never started" point is now that same frozen deadline + tolerance + 10 s, instead of a bound derived from `started_at`. Tests: `TestScheduledExecP3R1_TerminalBeforeDispatchNeverStarts` (abandoned and error; zero starts and a marker file never created), `TestScheduledExecP3R1_DelayedFirePastDeadline`, `TestScheduledExecP3R1_PauseBetweenCheckAndSend` (the late send carries the frozen deadline, sciontool refuses it, the marker is never created), and the interleaving matrix now asserts zero starts when recovery or a purge finishes the run before dispatch.
- **P3-R2 (Required), one slow target took every recovery slot.** `ClaimScheduledExecRunsForPoll` now chooses round-robin across target agents. Agents are taken in the order of their least recently polled run, one run each per round, before the in-flight limit applies; a second run of an agent is chosen only after every eligible agent has had one. The rotation persists through `last_polled_at`. The sweeper now starts each claimed poll as soon as any slot frees, instead of waiting for the slowest poll in a chunk. Tests: the reviewer's repro (`TestScheduledExecP3R2_SlowAgentPrefixDoesNotStarveHealthy`, a connected target that never answers status) and the store test `TestClaimScheduledExecRunsForPoll_FairAcrossTargets`.
- **P3-R3 (documented limitation, AC18 amended in design.md):** with `hub.conduit` off, a reconnecting agent session is refused, so outcome recovery works only over sessions that stay connected.
